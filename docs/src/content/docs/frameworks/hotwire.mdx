title: Hotwire
---

The Hotwire adapter provides a Stimulus controller for bridging custom events and Turbo morph protection for Voidable components.

## Install

### Gem (Rails with importmaps)

```bash
bundle add voidable-hotwire
```

The engine auto-registers importmap pins for `@voidable/ui` and `@voidable/ui-hotwire`, and includes the `void_attrs` view helper into ActionView.

`import "@voidable/ui"` registers every component up front. Server-rendered pages often use only a few; `rails generate voidable:install --components=autoloader` pins `@voidable/ui/autoloader` (and the Lit entry points it needs) instead, so each component is fetched the first time its tag appears, including tags that arrive in Turbo Drive visits, Streams and frames. See [Loading components](/getting-started/loading/) for when to prefer which. The pins are on `Voidable::Hotwire::CDN::AUTOLOADER_PINS` if you pin by hand.

Run `rails generate voidable:install` (see [Install generator](#install-generator) below) — it starts Turbo morph protection automatically. No manual edit needed.

### npm (Vite, esbuild, custom bundlers)

```bash
npm install @voidable/ui @voidable/theme @voidable/ui-hotwire
```

Start Turbo morph protection. No Stimulus controller is needed: Stimulus handles Voidable's custom events natively, so wire them with `data-action` (see [Usage in ERB templates](#usage-in-erb-templates)).

```js
import '@voidable/ui'; // or '@voidable/ui/autoloader' to load components on demand
import { VoidTurbo } from '@voidable/ui-hotwire';

VoidTurbo.start();
```

## Setting up Vite with Rails

This guide walks through replacing the default Rails asset pipeline (Propshaft + importmap) with plain Vite managed via npm. No additional gems are required — Vite builds assets to `public/` and Rails serves them as static files.

Start with a standard Rails 8 app:

```bash
rails new myapp --database=sqlite3
cd myapp
```

### Step 1: Remove Propshaft, importmap, and stimulus-rails

Remove the gems that Vite replaces from your `Gemfile`:

```ruby
# Remove these lines:
gem "propshaft"
gem "importmap-rails"
gem "stimulus-rails"
```

Run `bundle install` to update the lockfile.

Delete the importmap config and binary:

```bash
rm config/importmap.rb
rm bin/importmap
```

Remove the Propshaft assets initializer:

```bash
rm config/initializers/assets.rb
```

Remove the `config.assets.quiet = true` line from `config/environments/development.rb` — it relies on Propshaft which is no longer present.

Remove the `stale_when_importmap_changes` line from `app/controllers/application_controller.rb` — it's an importmap-rails feature.

### Step 2: Create package.json

Initialize a `package.json` in your Rails root and install Vite along with Hotwire and Voidable packages:

```bash
npm init -y
npm install vite @hotwired/turbo-rails @hotwired/stimulus
npm install @voidable/ui @voidable/theme @voidable/ui-hotwire
```

### Step 3: Configure Vite

Create `vite.config.ts` in your Rails root:

```ts
import { defineConfig } from "vite";

export default defineConfig({
  root: "app/javascript",
  build: {
    outDir: "../../public/assets",
    assetsDir: ".",
    emptyOutDir: true,
    manifest: true,
    rollupOptions: {
      input: "app/javascript/application.js",
    },
  },
  server: {
    origin: "http://localhost:5173",
  },
});
```

Key points:
- `root` points at `app/javascript` where your source lives
- `build.outDir` outputs to `public/assets/` so Rails serves them as static files
- `assetsDir: "."` prevents Vite from nesting output in an extra `assets/` subdirectory
- `manifest: true` generates a `manifest.json` for fingerprinted asset lookup
- `server.origin` ensures HMR assets reference the Vite dev server in development

### Step 4: Rewrite application.js

Replace the importmap-style `app/javascript/application.js` with ES imports:

```js
import "@hotwired/turbo-rails";
import { Application } from "@hotwired/stimulus";
import "@voidable/ui";
import { VoidTurbo } from "@voidable/ui-hotwire";

const app = Application.start();
VoidTurbo.start();
```

This is the baseline the install generator builds on. When you run `voidable:install --asset_pipeline vite` (Step 10), it appends CSS imports and ensures `VoidTurbo` is started — it does not undo this step.

Delete the importmap controller loader since Vite handles module resolution:

```bash
rm app/javascript/controllers/index.js
```

Update `app/javascript/controllers/application.js` to remove the `stimulus-loading` import (it's an importmap-only package):

```js
import { Application } from "@hotwired/stimulus";

const application = Application.start();
application.debug = false;
window.Stimulus = application;

export { application };
```

### Step 5: Update the layout

> Note: If you'll run `voidable:install --asset_pipeline vite` later (recommended), it overwrites `application.html.erb` with a complete Vite-ready layout. You can skip this step in that case.

Replace the Propshaft and importmap tags in `app/views/layouts/application.html.erb`:

```diff
- <%# Includes all stylesheet files in app/assets/stylesheets %>
- <%= stylesheet_link_tag :app, "data-turbo-track": "reload" %>
- <%= javascript_importmap_tags %>
+ <link rel="stylesheet" href="/assets/application.css" data-turbo-track="reload">
+ <script type="module" src="/assets/application.js" data-turbo-track="reload"></script>
```

In production, reference the fingerprinted filenames from the Vite manifest. A minimal helper:

```ruby
# app/helpers/vite_helper.rb
module ViteHelper
  def vite_asset_path(name)
    manifest_path = Rails.root.join("public/assets/.vite/manifest.json")
    if File.exist?(manifest_path)
      manifest = JSON.parse(File.read(manifest_path))
      entry = manifest[name]
      return "/assets/#{entry['file']}" if entry

      if name.end_with?(".css")
        manifest.each_value do |e|
          next unless e["css"]
          css_file = e["css"].find { |f| f.start_with?(File.basename(name, ".css")) }
          return "/assets/#{css_file}" if css_file
        end
      end
    end
    "/assets/#{name}"
  end
end
```

Vite extracts CSS imported from JavaScript into separate files, but these don't appear as top-level keys in the manifest — they're nested under the importing JS entry's `css` array. The fallback search handles this by scanning all entries for a matching CSS filename.

Then in your layout:

```erb
<link rel="stylesheet" href="<%= vite_asset_path('application.css') %>" data-turbo-track="reload">
<script type="module" src="<%= vite_asset_path('application.js') %>" data-turbo-track="reload"></script>
```

### Step 6: Add CSS entry point

Create `app/javascript/application.css` (or import your styles from `application.js`):

```css
@import "@voidable/theme";
```

Or import it from your JS entry point:

```js
import "@voidable/theme";
```

### Step 7: Add scripts to package.json

Add build and dev scripts to your `package.json`:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  }
}
```

### Step 8: Run Rails and Vite together

In development you need both processes running:

```bash
bin/rails server -p 3200    # one terminal
npm run dev                  # another terminal
```

If you want a single command, use a process manager of your choice (`foreman`, `overmind`, etc.) with a `Procfile.dev` — that's a matter of preference, not a requirement.

### Step 9: Add public/assets to .gitignore

Vite's build output is generated — don't commit it:

```gitignore
/public/assets
```

### Production build

Run `npm run build` before deploying. This generates fingerprinted files in `public/assets/` with a `.vite/manifest.json` for asset lookup.

In your `Dockerfile`, add the Vite build step:

```dockerfile
RUN npm install && npm run build
```

## Install generator

After adding the gem, run the install generator to scaffold a complete application layout with theme, importmap pins, and JS imports:

```bash
rails generate voidable:install
```

### Options

| Option | Values | Default | Description |
|---|---|---|---|
| `--layout` | `topbar`, `sidebar`, `switching` | `topbar` | Application layout style |
| `--asset_pipeline` | `importmap`, `vite` | `importmap` | Asset pipeline integration |
| `--components` | `all`, `autoloader` | `all` | `all` registers every component up front; `autoloader` loads each when its tag first appears |

```bash
# Defaults: topbar layout, importmap pipeline
rails generate voidable:install

# Sidebar with fixed nav
rails generate voidable:install --layout sidebar

# Both layouts with a cookie-based toggle
rails generate voidable:install --layout switching

# For apps using Vite (see "Setting up Vite with Rails" above)
rails generate voidable:install --layout switching --asset_pipeline vite

# Load components on demand instead of registering all of them
rails generate voidable:install --components autoloader
```

The `--asset_pipeline vite` flag changes the destination paths for generated assets from `app/assets/stylesheets/` and `app/assets/javascripts/` to `app/javascript/`, adds CSS `@import` statements to `application.js`, and creates a `ViteHelper` for production manifest lookup. It does **not** modify `config/importmap.rb`.

### Before you run the generator

If you're using Devise, `rails generate devise:install` will warn that no `root to:` route exists. Define one before testing (any controller works — `root to: "samples#index"` for example). The gem's "Dashboard" sidebar link falls back gracefully to `/` when no root route is defined, but having one makes it useful.

The install generator runs `bin/rails active_storage:install` automatically (added in 0.7.0), which queues an Active Storage migration alongside any scaffold migrations. Run `bin/rails db:migrate` after both the install generator and any scaffold generators to apply all pending migrations.

#### Switching mode

When `--layout switching` is used, the generator additionally creates topbar and sidebar variants of the layout file (`topbar.html.erb`, `sidebar.html.erb`) and CSS files (`voidable-layout-topbar.css`, `voidable-layout-sidebar.css`), a `SettingsController` that toggles the layout cookie, a `POST /toggle_layout` route, and injects a `layout :resolve_layout` method into `ApplicationController` that reads the `:layout` cookie to pick the active layout, defaulting to `"topbar"`.

### Settings menu

All layouts include a shared `_settings_menu.html.erb` partial rendered inside a `void-popover`. The gear icon opens a menu with:

- **Profile** link (when Devise is available and user is signed in)
- **Dark mode** toggle via `void-switch`
- **Layout switch** button (switching mode only)

The partial accepts locals to configure its behavior:

```erb
<%= render "layouts/settings_menu",
  popover_position: "bottom",
  layout_toggle: true,
  layout_toggle_icon: "layout-sidebar-left-collapse",
  layout_toggle_label: "Switch to sidebar" %>
```

| Local | Type | Description |
|---|---|---|
| `popover_position` | `string` | Popover direction: `"top"` (sidebar) or `"bottom"` (topbar) |
| `layout_toggle` | `boolean` | Show the layout switch button |
| `layout_toggle_icon` | `string` | Tabler icon name for the switch button |
| `layout_toggle_label` | `string` | Button label text |

### Theme toggle

The generated layouts include a theme toggle script that syncs `void-switch` state with `localStorage` and respects system preference on first load. The script listens for `void-change` events and persists the choice across Turbo navigations:

```html
<script>
  (function() {
    const html = document.documentElement;

    function applyTheme() {
      if (!localStorage.getItem('theme')) {
        const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
        html.setAttribute('data-theme', prefersDark ? 'dark' : 'light');
      } else {
        html.setAttribute('data-theme', localStorage.getItem('theme'));
      }
    }

    function syncToggle() {
      const toggle = document.getElementById('theme-toggle');
      if (toggle) {
        toggle.toggleAttribute('checked', html.getAttribute('data-theme') === 'dark');
      }
    }

    applyTheme();
    syncToggle();
    document.addEventListener('turbo:load', syncToggle);

    document.addEventListener('void-change', (e) => {
      if (e.target.id !== 'theme-toggle') return;
      const next = e.detail.checked ? 'dark' : 'light';
      html.setAttribute('data-theme', next);
      localStorage.setItem('theme', next);
    });
  })();
</script>
```

## Turbo morph protection

`VoidTurbo.start()` makes Turbo page morphs (`<meta name="turbo-refresh-method" content="morph">`, `turbo_stream` refreshes, `Turbo.morphChildren`) safe for every `<void-*>` component. On `turbo:before-morph-element` it calls the element's pre-morph hook with Turbo's incoming element. What survives a morph:

- **The component's own DOM.** Before the morph compares an element, the adapter calls its `voidBeforeMorph()` hook: the structure the component rendered (native inputs, wrappers, icons, list items) is set aside and the element is left looking like its server markup, so the morph only diffs what the server sent. Right after the morph the same nodes go back, so nothing is rebuilt: a field you are typing in keeps its focus, caret, text and scroll position, an unfocused field keeps what was typed, and scroll positions, slider positions and chart state are kept. In browsers with `Element.moveBefore` (Chromium, recent Firefox) the nodes never leave the document; elsewhere they are put back with the same focus, caret, text and scroll, and the only difference is that `blur` and `focus` events fire.
- **The server's changes win; the client's state survives otherwise.** For every reflected property of every component (`open`, `checked`, `pressed`, `collapsed`, `active`, `value`, `indeterminate`, ...), the element remembers what the server last rendered. An attribute the server changed since then, including one it removed, is applied; every other one keeps the client's value. So a dialog, drawer or accordion item the user opened (a dialog or drawer still modal, with focus and typed text inside; see [Overlays](/components/overlays/#server-driven-pages)), a toggle they pressed, a collapsed sidebar or the carousel's current slide survive a morph that does not change them, and the server can still close, uncheck or move them by rendering a different value. Groups that keep their state in their children (toggle-group, segmented-control, radio-group, checkbox-group, tabs) re-apply it to children the morph added or replaced. Text typed but not committed yet (number-input, editable) survives until it is committed, unless the server changes the value. A value the server changes also becomes the form control's reset default, as a native input's default follows its `value` attribute.
- **What you are typing is yours while focus is in the field.** A refresh morph that arrives while you type never rewrites the text of the field you are in, as a browser never rewrites a native field from its `value` attribute; the server's value is applied by the next morph after focus has left, if it changed. Nothing typed is lost and focus never leaves the field, with or without `Element.moveBefore`.
- **A selection the server removed falls back** instead of going blank: tabs whose selected panel is gone select the panel the server's `value` names, else the first enabled one; a select whose picked option is gone takes the server's `value`, else the first enabled option.
- **Unchanged components are skipped.** A component whose server markup (attributes and content) is identical to what the server sent last time is left out of the morph together with everything inside it, since the morph could only keep its state. That makes re-rendering a mostly unchanged page cheap; it also means a page script's own changes inside such a component are not undone by Turbo.
- **Attributes the component manages on itself** (`role`, `tabindex`, `aria-checked` and the like) are carried onto the incoming element whenever the server markup does not set them, so the morph leaves them alone. Anything the server markup sets is applied. If a page script keeps removing one of them, the component stops putting it back after ten attempts within a second (`@voidable/ui/dev` reports it).
- **Without the adapter** (a plain idiomorph or morphdom call, `innerHTML` on a parent, a framework replacing children) components still end up correct: one that loses its rendered DOM renders it again, attributes it manages are put back, and a cloned or re-parsed copy of a rendered element (a page-cache snapshot) renders exactly one set of its DOM. Focus and selection inside a rebuilt component are lost in that case.

Turbo's page cache restores pages from a snapshot of the rendered page; components clean up the copied DOM when they reconnect, so a restored page shows each component once.

To leave a subtree completely alone (Turbo neither morphs nor replaces it), give it an id and `data-turbo-permanent`:

```erb
<div id="player" data-turbo-permanent>…</div>
```

A `<void-select>` with thousands of options costs as much to morph as a plain `<select>` of that size, a second or more: that is Turbo diffing every option. For very large option lists give the field an id and `data-turbo-permanent`, or use `<void-combobox>`, which renders only the options that match what was typed.

## Usage in ERB templates

With the `void_attrs` helper (gem only):

`void_attrs` returns a Ruby hash (`{ data: { action: "void-click->form#submit" } }`) that you splat into a Rails tag helper:

```erb
<%= tag.void_button "Save", variant: "filled",
      **void_attrs("void-click", "form#submit") %>

<%= tag.void_input placeholder: "Email",
      **void_attrs("void-change", "search#filter") %>
```

With manual data attributes, use Stimulus `data-action` directly; Stimulus listens for Voidable's custom events like any other DOM event:

```erb
<void-button variant="filled" data-action="void-click->form#submit">
  Save
</void-button>

<void-input
  placeholder="Email"
  data-action="void-change->search#filter"
></void-input>
```

## Scaffolds

The gem overrides Rails' default scaffold templates so `rails generate scaffold` produces Voidable-styled views automatically. The engine registers templates via `config.generators.templates.unshift`, requiring no extra configuration.

### Generated views

The gem scaffolds use an index-with-modal architecture: the `show`,
`edit`, and `new` actions all render the index template with the
appropriate modal open. Direct URL navigation to a resource lands on
the same page as clicking a row.

- **Index** (`index.html.erb`) — page header with title, subtitle, and
  "New" button; hoverable table whose rows are clickable
  (`class="row-clickable" data-href="..."`) and open the show modal;
  pagination via `<void-pagination>` when Pagy is configured; empty
  state when no records exist. Below the table, three conditional
  modals:
  - **Show modal** — opened by clicking a row or navigating to
    `/resources/:id`. Renders a `<dl class="detail-grid">` of the
    record's attributes plus Edit / Delete action buttons.
  - **Edit modal** (`@edit_mode`) — opened by clicking Edit inside
    the show modal or navigating to `/resources/:id/edit`. Renders
    the form partial.
  - **New modal** (`@new_mode`) — opened by clicking the "New" header
    button or navigating to `/resources/new`. Renders the form partial.
- **Form partial** (`_form.html.erb`) — `<void-field>` per attribute,
  full-width divider above the action row, Submit + Back buttons. No
  `<void-card>` wrapper — that's externally applied only when the form
  is rendered standalone, so the dialog body doesn't show a nested
  border.
- **Turbo partial** (`_<resource>.html.erb`) — Rails-conventional
  partial used by Turbo Stream responses.
- **Stub views** (`show.html.erb`, `edit.html.erb`, `new.html.erb`) —
  shipped as empty stubs with an HTML comment explaining they are
  never rendered (the controller `render :index` instead). Safe to
  delete.

The scaffold controller's `show`, `edit`, and `new` actions each load
pagy data and call `render :index`. `update` and `create` failures
also fall back to `render :index` with the matching mode flag so form
errors appear in the modal.

### Component mapping by type

| Attribute type | Voidable component |
|---|---|
| `string` | `void-input` |
| `text` | `void-textarea` |
| `integer` | `void-number-input` |
| `float`, `decimal` | `void-number-input` with `step="any"` |
| `boolean` | `void-switch` (form) / `void-badge` (show, index) |
| `date` | `void-date-picker` |
| `datetime` | `void-input` with `type="datetime-local"` |
| `time` | `void-input` with `type="time"` |
| `references` | `void-select` |
| `password` | `void-input` with `type="password"` |
| `attachment` | Rails `file_field` |
| `attachments` | Rails `file_field` with `multiple: true` |

### Pagination

Scaffolds use [Pagy](https://github.com/ddnexus/pagy) for pagination
when the gem is bundled. Add it to your Gemfile alongside
`voidable-hotwire`:

```bash
bundle add pagy
rails generate voidable:install   # re-run to wire it up if you missed it the first time
```

The install generator detects Pagy and, when present:

- Creates `config/initializers/pagy.rb` with `require "pagy"` and
  `require "pagy/toolbox/paginators/method"` (Pagy 9+ API).
- Adds `include Pagy::Method` to `ApplicationController`.

If Pagy is not bundled when the generator runs, it prints a
recommendation and skips the configuration. Re-run the generator
after `bundle add pagy` to complete the wiring.

In scaffolded controllers, the `index`, `show`, `edit`, and `new`
actions all call:

```ruby
@pagy, @<plural> = pagy(<Model>.all)
```

The index template renders `<void-pagination>` at the bottom of the
table when `@pagy.pages > 1`. `voidable-layout.js` listens for
`void-change` events on `<void-pagination>` and translates clicks to
`?page=N` URL changes via `Turbo.visit`.

### Delete confirmation

The Delete button in the show modal opens a secondary `<void-dialog>`
for confirmation. The gem's layout JS handles open/close via data
attributes — no inline `onclick` handlers are needed:

```erb
<void-button data-open-dialog="resource-delete-dialog">Delete</void-button>

<void-dialog id="resource-delete-dialog" heading="Delete order" size="sm">
  <p class="danger-zone-description">Are you sure? This action cannot be undone.</p>
  <div class="action-bar">
    <void-button variant="ghost" size="sm"
      data-close-dialog="resource-delete-dialog">Cancel</void-button>
    <void-button color="error" size="sm"
      ><a href="<%= url_for(@order) %>" data-turbo-method="delete">Delete</a></void-button>
  </div>
</void-dialog>
```

`voidable-layout.js` listens for clicks on `[data-open-dialog]` and
`[data-close-dialog]` and toggles the targeted dialog's `open`
attribute. The same handler is used by the Devise account-deletion
flow.

### Back navigation

Closing a resource modal navigates back to the index. The layout JS
remembers the user's index URL (with pagination/filter query string)
in `sessionStorage` whenever a row is clicked, keyed by the
destination path. When `<void-dialog data-close-href="...">` closes,
the handler navigates to the saved URL — falling back to the dialog's
`data-close-href` for direct URL navigations where no saved state
exists. `void-close` does not bubble, so the handler listens on the
document in the capture phase, and it navigates only when no listener
cancelled the close.

While a resource modal is open, the index template emits
`<meta name="turbo-cache-control" content="no-cache">`. Light-DOM
custom-element children are captured verbatim in Turbo's snapshot
cache, and restoring them would duplicate the dialog body — opting
out of caching avoids this.

## Devise

The gem includes pre-styled [Devise](https://github.com/heartcombo/devise) views that match the Voidable design system.

### Setup order

The `voidable:install` generator auto-runs `voidable:devise_views` **only if Devise is already loaded** at generator execution time. If you add Devise to your app, the recommended order is:

```bash
# 1. Add both gems
bundle add voidable-hotwire
bundle add devise

# 2. Set up Devise first
rails generate devise:install
rails generate devise User
rails db:migrate

# 3. Then run the Voidable installer — Devise views are auto-installed
rails generate voidable:install --layout switching
```

If you installed Voidable **before** Devise, run the Devise views generator separately afterward:

```bash
rails generate voidable:devise_views
```

This copies all Devise views into `app/views/devise/` with Voidable components already wired up. The following views are included:

| View | Description |
|---|---|
| `sessions/new` | Sign-in form with email and password fields |
| `registrations/new` | Sign-up form with email, password, and confirmation |
| `registrations/edit` | Account settings with profile update and danger zone for account deletion |
| `passwords/new` | Forgot password form |
| `passwords/edit` | Reset password form |
| `confirmations/new` | Resend confirmation instructions |
| `unlocks/new` | Resend unlock instructions |
| `shared/_links` | Navigation links between Devise views (sign in, sign up, forgot password) |
| `shared/_error_messages` | Validation error display using `void-alert` |

### Sign-in form

A typical sign-in view using Voidable components:

```erb
<div style="max-width: 28rem; margin: 0 auto; padding: 2rem;">
  <void-card>
    <div style="padding: var(--void-space-6);">
      <h1 style="margin: 0 0 var(--void-space-5) 0; font-family: var(--void-font-sans); font-size: var(--void-text-xl); font-weight: var(--void-weight-bold); color: var(--void-color-text);">Sign in</h1>

      <%= form_for(resource, as: resource_name, url: session_path(resource_name), html: { style: "display: flex; flex-direction: column; gap: var(--void-space-4);" }) do |f| %>
```

### Password visibility toggle

`void-action-input` provides a built-in action button for password reveal. The generated layouts include a global event listener that handles the toggle automatically:

```html
<script>
  document.addEventListener('void-action', (e) => {
    const el = e.target;
    if (el.tagName === 'VOID-ACTION-INPUT' && (el.type === 'password' || el.type === 'text')) {
      const visible = el.type === 'text';
      el.type = visible ? 'password' : 'text';
      el.icon = visible ? 'eye' : 'eye-off';
    }
  });
</script>
```

## Development warnings

`voidable-hotwire` loads `@voidable/ui/dev` in the **development environment only**, so a misspelled attribute, an invalid value or a child in the wrong parent shows up as a `[voidable]` warning in the browser console, including markup your ERB and Turbo Streams render at runtime. `rails generate voidable:install` sets it up:

- importmap: `pin "@voidable/ui/dev"` (development only) and `<%= voidable_dev_tags %>` after `javascript_importmap_tags` in the layout. The helper renders nothing in other environments.
- Vite: `if (import.meta.env.DEV) import("@voidable/ui/dev");` in `application.js`.

Change it in `config/initializers/voidable.rb`:

```ruby
Voidable::Hotwire.dev_warnings = false   # off everywhere
Voidable::Hotwire.dev_warnings = true    # on, even outside development
Voidable::Hotwire.dev_warnings = :throw  # thrown errors, for system tests
```

See [Development warnings](/getting-started/development-warnings/) for what it reports.

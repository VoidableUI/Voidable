The Alpine adapter provides directives for wiring custom events to Alpine handlers and preserving element state during Livewire morphs. A companion Laravel package adds Blade directives for easy asset loading.

## Install

```bash
npm install @voidable/ui @voidable/theme @voidable/ui-alpine
```

For Laravel projects, also install the Composer package:

```bash
composer require voidable/laravel
```

## Load the components

`import '@voidable/ui'` registers every component up front. For Livewire and Blade pages that use a few components, `import '@voidable/ui/autoloader'` loads each one the first time its tag appears, including tags Livewire adds when it morphs the page. See [Loading components](/getting-started/loading/).

## Register the Alpine plugin

For standalone Alpine projects, import and start Alpine yourself:

```js
import Alpine from 'alpinejs';
import { VoidableAlpine } from '@voidable/ui-alpine';

Alpine.plugin(VoidableAlpine);
Alpine.start();
```

### With Livewire

Livewire 4 bundles Alpine and starts it automatically — do not import or start Alpine yourself. Instead, register the plugin via the `alpine:init` event and call `registerLivewireHooks` to register the Livewire morph hook that keeps `<void-*>` component state across re-renders:

```js
import { VoidableAlpine, registerLivewireHooks } from '@voidable/ui-alpine';
import '@voidable/ui';
import '@voidable/theme';

document.addEventListener('alpine:init', () => {
    window.Alpine.plugin(VoidableAlpine);
});

registerLivewireHooks();
```

The plugin registers two directives:

- `x-void-on` — Wires Voidable custom events to Alpine handlers
- `x-void-preserve` — Sets `wire:ignore` on the element, so Livewire leaves it and its children alone

## Usage

Use `x-void-on:{event}` to handle custom events within `x-data` scopes:

```html
<div x-data="{ count: 0 }">
  <void-button
    variant="filled"
    x-void-on:void-click="count++"
  >
    Clicked <span x-text="count"></span> times
  </void-button>

  <void-input aria-label="Search"
    placeholder="Search"
    x-void-on:void-change="$dispatch('filter', $event.detail)"
  ></void-input>
</div>
```

## Livewire morph protection

With `registerLivewireHooks()`, Livewire re-renders are safe for every `<void-*>` component: on Livewire's `morph.updating` hook the element's pre-morph hook runs with Livewire's incoming element. What survives a morph:

- **The component's own DOM.** Before the morph compares an element, the adapter calls its `voidBeforeMorph()` hook: the structure the component rendered (native inputs, wrappers, icons, list items) is set aside and the element is left looking like its server markup, so the morph only diffs what the server sent. Right after the morph the same nodes go back, so nothing is rebuilt: a field you are typing in keeps its focus, caret, text and scroll position, an unfocused field keeps what was typed, and scroll positions, slider positions and chart state are kept. In browsers with `Element.moveBefore` (Chromium, recent Firefox) the nodes never leave the document; elsewhere they are put back with the same focus, caret, text and scroll, and the only difference is that `blur` and `focus` events fire.
- **The server's changes win; the client's state survives otherwise.** For every reflected property of every component (`open`, `checked`, `pressed`, `collapsed`, `active`, `value`, `indeterminate`, ...), the element remembers what the server last rendered. An attribute the server changed since then, including one it removed, is applied; every other one keeps the client's value. So a dialog, drawer or accordion item the user opened (a dialog or drawer still modal, with focus and typed text inside; see [Overlays](/components/overlays/#server-driven-pages)), a toggle they pressed, a collapsed sidebar or the carousel's current slide survive a morph that does not change them, and the server can still close, uncheck or move them by rendering a different value. Groups that keep their state in their children (toggle-group, segmented-control, radio-group, checkbox-group, tabs) re-apply it to children the morph added or replaced. Text typed but not committed yet (number-input, editable) survives until it is committed, unless the server changes the value. A value the server changes also becomes the form control's reset default, as a native input's default follows its `value` attribute.
- **What you are typing is yours while focus is in the field.** A morph that arrives while you type (Livewire's reply to `wire:model.live` or `$wire.set`, which echoes a value a few keys behind) never rewrites the text of the field you are in, as a browser never rewrites a native field from its `value` attribute; the server's value is applied by the next morph after focus has left, if it changed. Nothing typed is lost and focus never leaves the field.
- **A selection the server removed falls back** instead of going blank: tabs whose selected panel is gone select the panel the server's `value` names, else the first enabled one; a select whose picked option is gone takes the server's `value`, else the first enabled option.
- **A select keeps its choice whatever the timing.** Morph libraries re-sync a native `<select>` from its options' `selected` attributes as they patch it. `<void-select>` holds the choice itself and writes it back into the select after every patch, through the adapter or, without one, whenever its options change; a form that builds its data in between (a submit, `new FormData(form)`) gets the choice as well. The server still wins by sending a different `value` or marking other options `selected`, and a script that sets the native select's value (a framework binding) is followed.
- **Unchanged components are skipped.** A component whose server markup (attributes and content) is identical to what the server sent last time is left out of the morph together with everything inside it, since the morph could only keep its state. That makes re-rendering a mostly unchanged page cheap; it also means a page script's own changes inside such a component are not undone by Livewire.
- **Attributes the component manages on itself** (`role`, `tabindex`, `aria-checked` and the like) are carried onto the incoming element whenever the server markup does not set them, so the morph leaves them alone. Anything the server markup sets is applied. If a page script keeps removing one of them, the component stops putting it back after ten attempts within a second (`@voidable/ui/dev` reports it).
- **Without the adapter** (a plain idiomorph or morphdom call, `innerHTML` on a parent, a framework replacing children) components still end up correct: one that loses its rendered DOM renders it again, attributes it manages are put back, and a cloned or re-parsed copy of a rendered element (a page-cache snapshot) renders exactly one set of its DOM. Focus and selection inside a rebuilt component are lost in that case.

To leave a subtree completely alone, add `wire:ignore` (or the `x-void-preserve` directive, which adds it for you):

```html
<div wire:ignore>…</div>

<void-dialog x-void-preserve>
  <void-dialog-title>Client-owned</void-dialog-title>
  <void-dialog-body>
    <p>Livewire never touches this dialog or its content.</p>
  </void-dialog-body>
</void-dialog>
```

`wire:ignore.self` only protects the element's own attributes; Livewire still morphs its children.

## Laravel Blade directives

The `voidable/laravel` package provides Blade directives for loading assets without a build step:

```blade
<head>
  @voidableStyles
  @voidableScripts
</head>
```

`@voidableScripts` outputs a `<script type="module">` tag that imports the component definitions and registers the Alpine plugin. `@voidableStyles` loads the theme CSS.

When using Vite to bundle your assets (the standard Laravel + Livewire setup), these directives are unnecessary. Import everything in your `app.js` entry point and load it with the `@vite` directive instead:

```blade
<head>
  @vite(['resources/css/app.css', 'resources/js/app.js'])
</head>
```

## Charts from server data

The charts take their data as the JSON `data` attribute (a gauge's `zones` too), so the first response already draws them. The `voidable/laravel` package has Blade components that write it from PHP arrays (or a JSON string); every other attribute passes through as written:

```blade
<x-voidable::bar-chart aria-label="Revenue by quarter" show-value
    :data="['labels' => ['Q1', 'Q2'], 'series' => [['name' => '2025', 'values' => [4, 8]]]]" />
<x-voidable::line-chart aria-label="Visitors" :data="$visits" />
<x-voidable::donut-chart aria-label="Traffic by source" show-total :data="['segments' => $sources]" />
<x-voidable::gauge aria-label="Disk usage" :value="72" unit="%"
    :zones="[['from' => 0, 'to' => 60, 'color' => 'var(--void-color-success)']]" />
```

A Livewire update that leaves a chart's data unchanged leaves the chart alone (no new animation); changed data redraws it. Each chart carries a visually hidden data table captioned with `aria-label`, and `show-table` shows it below the chart. The example app's charts lab (`/lab/charts`) is tested against real Livewire in `tests/browser/server/laravel/charts.spec.ts`.

## Tables the server drives

`<void-table manual>` never reorders or hides a row: it fires `void-sort`, `void-filter` and `void-change`, and the Livewire component answers by rendering the order, the visible rows, `sort`, `sort-direction`, `filter` and `value`. The `voidable/laravel` package has Blade components for the table and its parts (`<x-voidable::table>`, `table-filter`, `table-empty`, `table-selection`, `table-select-all`). `value` and `keys` take a PHP array and are written as the JSON attributes the element reads; every other attribute passes through as written.

```blade
{{-- resources/views/livewire/orders.blade.php --}}
<x-voidable::table manual selectable aria-label="Orders"
    :sort="$sort" :sort-direction="$direction" :total-rows="$total" :value="$selected"
    x-void-on:void-sort="$wire.sortBy($event.detail.column, $event.detail.direction)"
    x-void-on:void-change="$wire.select($event.detail.value, $event.detail.all)">
  <table>
    <thead><tr>
      <th data-stack="select"><input type="checkbox" aria-label="Select all rows"></th>
      <th data-key="name" data-sort>Name</th>
    </tr></thead>
    <tbody>
      @foreach ($orders as $order)
        <tr wire:key="order-{{ $order->id }}" data-value="{{ $order->id }}">
          <td><input type="checkbox" aria-label="Select order {{ $order->id }}"></td>
          <td>{{ $order->name }}</td>
        </tr>
      @endforeach
    </tbody>
  </table>
  <x-voidable::table-selection hidden><span data-count></span> selected</x-voidable::table-selection>
  <x-voidable::table-select-all hidden>
    <button type="button">Select all {{ number_format($total) }} rows</button>
  </x-voidable::table-select-all>
</x-voidable::table>
```

```php
// app/Livewire/Orders.php
public string $sort = 'name';
public string $direction = 'ascending';
public array $selected = [];
public bool $allSelected = false;

public function sortBy(string $column, string $direction): void
{
    [$this->sort, $this->direction] = [$column, $direction];
    $this->resetPage();
}

public function select(array $value, bool $all): void
{
    // $all: the user chose every row of the query, not only this page's.
    [$this->selected, $this->allSelected] = [$value, $all];
}
```

With `total-rows` greater than the rows on the page, the part inside `table-select-all` appears once the header checkbox is checked; its button sets `all-selected` and fires `void-change` with `all: true`, and the component applies the bulk action to the whole query. Native checkboxes in the rows (above) are the right choice at thousands of rows. The table's words (the select-all name, the count announcement) follow `lang`; select-all by keyboard is off until you bind it with `:keys="['selectAll' => ['Control+a', 'Meta+a']]"`. See [Table](/components/table/#server-mode-manual).

## Development warnings

A misspelled attribute, an invalid value or a child in the wrong parent does nothing and says nothing. In Laravel, `@voidableScripts` also loads `@voidable/ui/dev` when `voidable.dev_warnings` is on, which by default is the `local` environment only (`VOIDABLE_DEV_WARNINGS=false` turns it off, `VOIDABLE_DEV_WARNINGS=throw` makes warnings throw for browser tests). Without Laravel, import it from your bundle in development only:

```js
if (import.meta.env.DEV) import('@voidable/ui/dev');
```

It also checks what Livewire and Blade render at runtime. See [Development warnings](/getting-started/development-warnings/).

## Check the markup

The development warnings only see pages you open. The `voidable` tool reads the files instead, so it covers every template at once, in the editor and in CI. Install it with `curl -fsSL https://voidable.dev/install.sh | sh` (see [For AI agents](/getting-started/for-agents/#install-it)), then run:

```sh
voidable check resources/views
```

It reports unknown elements, attributes and values, children in the wrong parent, controls with no accessible name and every form renamed in 0.8, each with what to write instead (see [Upgrading to 0.8](/guides/upgrading/)).

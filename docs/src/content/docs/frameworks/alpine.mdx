The Alpine adapter provides directives for wiring custom events to Alpine handlers and preserving element state during Livewire morphs. A companion Laravel package adds Blade directives for easy asset loading.

## Install

```bash
npm install @voidable/ui @voidable/theme @voidable/ui-alpine
```

For Laravel projects, also install the Composer package:

```bash
composer require voidable/laravel
```

## Load the components

`import '@voidable/ui'` registers every component up front. For Livewire and Blade pages that use a few components, `import '@voidable/ui/autoloader'` loads each one the first time its tag appears, including tags Livewire adds when it morphs the page. See [Loading components](/getting-started/loading/).

## Register the Alpine plugin

For standalone Alpine projects, import and start Alpine yourself:

```js
import Alpine from 'alpinejs';
import { VoidableAlpine } from '@voidable/ui-alpine';

Alpine.plugin(VoidableAlpine);
Alpine.start();
```

### With Livewire

Livewire 4 bundles Alpine and starts it automatically — do not import or start Alpine yourself. Instead, register the plugin via the `alpine:init` event and call `registerLivewireHooks` to register Livewire morph lifecycle hooks that snapshot and restore void-* element internal state during re-renders:

```js
import { VoidableAlpine, registerLivewireHooks } from '@voidable/ui-alpine';
import '@voidable/ui';
import '@voidable/theme';

document.addEventListener('alpine:init', () => {
    window.Alpine.plugin(VoidableAlpine);
});

registerLivewireHooks();
```

The plugin registers two directives:

- `x-void-on` — Wires Voidable custom events to Alpine handlers
- `x-void-preserve` — Sets `wire:ignore` on the element, so Livewire leaves it and its children alone

## Usage

Use `x-void-on:{event}` to handle custom events within `x-data` scopes:

```html
<div x-data="{ count: 0 }">
  <void-button
    variant="filled"
    x-void-on:void-click="count++"
  >
    Clicked <span x-text="count"></span> times
  </void-button>

  <void-input
    placeholder="Search"
    x-void-on:void-change="$dispatch('filter', $event.detail)"
  ></void-input>
</div>
```

## Livewire morph protection

With `registerLivewireHooks()`, Livewire re-renders are safe for every `<void-*>` component: on Livewire's `morph.updating` hook the element's pre-morph hook runs, and the component's `value` / `checked` are restored after the morph unless the server rendered a different value. What survives a morph:

- **The component's own DOM.** Before the morph compares an element, the adapter calls its `voidBeforeMorph()` hook: the structure the component rendered (native inputs, wrappers, icons, list items) is set aside and the element is left looking like its server markup, so the morph only diffs what the server sent. Right after the morph the same nodes go back, so nothing is rebuilt: a field you are typing in keeps its focus, caret and text (in browsers with `Element.moveBefore`, currently Chromium; elsewhere focus and caret are restored after the move), an unfocused field keeps what was typed, and scroll positions, slider positions and chart state are kept.
- **Attributes the component manages on itself** (`role`, `tabindex`, `aria-checked` and the like, and reflected properties still at their default, such as `size="md"`) are carried onto the incoming element whenever the server markup does not set them, so the morph leaves them alone.
- **Server-controlled state follows the server.** Anything the server markup sets (`label`, `value`, `disabled`, ...) is applied. Client state such as `open` or `checked` is kept only while the server keeps rendering the same value it rendered last time; as soon as the server renders a different value (including removing it), the server wins. A dialog, drawer or popover the user opened therefore stays open (still modal, with focus and typed text inside) until the server changes its `open`; see [Overlays](/components/overlays/#server-driven-pages).
- **Without the adapter** (a plain idiomorph or morphdom call, `innerHTML` on a parent, a framework replacing children) components still end up correct: one that loses its rendered DOM renders it again, attributes it manages are put back, and a cloned or re-parsed copy of a rendered element (a page-cache snapshot) renders exactly one set of its DOM. Focus and selection inside a rebuilt component are lost in that case.

To leave a subtree completely alone, add `wire:ignore` (or the `x-void-preserve` directive, which adds it for you):

```html
<div wire:ignore>…</div>

<void-dialog x-void-preserve>
  <p>Livewire never touches this dialog or its content.</p>
</void-dialog>
```

`wire:ignore.self` only protects the element's own attributes; Livewire still morphs its children.

## Laravel Blade directives

The `voidable/laravel` package provides Blade directives for loading assets without a build step:

```blade
<head>
  @voidableStyles
  @voidableScripts
</head>
```

`@voidableScripts` outputs a `<script type="module">` tag that imports the component definitions and registers the Alpine plugin. `@voidableStyles` loads the theme CSS.

When using Vite to bundle your assets (the standard Laravel + Livewire setup), these directives are unnecessary. Import everything in your `app.js` entry point and load it with the `@vite` directive instead:

```blade
<head>
  @vite(['resources/css/app.css', 'resources/js/app.js'])
</head>
```

## Development warnings

A misspelled attribute, an invalid value or a child in the wrong parent does nothing and says nothing. In Laravel, `@voidableScripts` also loads `@voidable/ui/dev` when `voidable.dev_warnings` is on, which by default is the `local` environment only (`VOIDABLE_DEV_WARNINGS=false` turns it off, `VOIDABLE_DEV_WARNINGS=throw` makes warnings throw for browser tests). Without Laravel, import it from your bundle in development only:

```js
if (import.meta.env.DEV) import('@voidable/ui/dev');
```

It also checks what Livewire and Blade render at runtime. See [Development warnings](/getting-started/development-warnings/).

The LiveView adapter uses a dual-package architecture (npm + Hex) to bridge Voidable custom events to Phoenix LiveView's server-side event handling.

## Install

Install the JavaScript package:

```bash
npm install @voidable/ui @voidable/theme @voidable/ui-liveview
```

Add the Hex package to `mix.exs`. It shares its version number with the npm packages, so use the same version for both:

<Code lang="elixir" code={`defp deps do
  [
    {:live_voidable, "${hexRequirement}"}
  ]
end`} />

## Load the components

`import '@voidable/ui'` registers every component up front. LiveView pages usually use a few, and patches add more over time; `import '@voidable/ui/autoloader'` fetches each component the first time its tag appears in the page or in a patch. Without a bundler, vendor the files with `voidable install` and import `@voidable/ui/autoloader.js` through the import map it prints. See [Loading components](/getting-started/loading/).

## Register the LiveView hook

Add the `VoidEvent` hook to your LiveSocket:

```js
import { VoidHooks } from '@voidable/ui-liveview';

let liveSocket = new LiveSocket('/live', Socket, {
  hooks: { ...VoidHooks }
});
```

The hook listens for Voidable custom events on the element and forwards them to the server via `pushEvent`.

## Usage in HEEx templates

Attach the hook with `phx-hook` and add `phx-update="ignore"` to prevent LiveView from clobbering client-managed state:

```heex
<void-button
  variant="filled"
  phx-hook="VoidEvent"
  phx-update="ignore"
  data-void-events="void-click"
>
  Submit
</void-button>

<void-input
  placeholder="Search"
  phx-hook="VoidEvent"
  phx-update="ignore"
  data-void-events="void-change"
></void-input>
```

## Handle events on the server

Events arrive as standard LiveView events:

```elixir
def handle_event("void-click", _params, socket) do
  {:noreply, assign(socket, :submitted, true)}
end

def handle_event("void-change", %{"value" => value}, socket) do
  {:noreply, assign(socket, :query, value)}
end
```

## DOM preservation

`VoidDOM` is a separate export from `@voidable/ui-liveview` (not part of `VoidHooks`). Wire its callback into your `LiveSocket` constructor via the `dom` option so morphdom patches are safe for every `<void-*>` component:

```js
import { VoidHooks, VoidDOM } from '@voidable/ui-liveview';

let liveSocket = new LiveSocket('/live', Socket, {
  hooks: { ...VoidHooks },
  dom: {
    onBeforeElUpdated(from, to) {
      VoidDOM.onBeforeElUpdated(from, to);
    },
  },
});
```

`onBeforeElUpdated` calls the element's pre-morph hook with `to`, the server's version of the element (each element records the server's attributes itself when it first connects, so there is no `onNodeAdded` to wire). What survives a patch:

- **The component's own DOM.** Before the morph compares an element, the adapter calls its `voidBeforeMorph()` hook: the structure the component rendered (native inputs, wrappers, icons, list items) is set aside and the element is left looking like its server markup, so the morph only diffs what the server sent. Right after the morph the same nodes go back, so nothing is rebuilt: a field you are typing in keeps its focus, caret, text and scroll position, an unfocused field keeps what was typed, and scroll positions, slider positions and chart state are kept. In browsers with `Element.moveBefore` (currently Chromium) the nodes never leave the document; elsewhere (Safari, Firefox) they are put back with the same focus, caret, text and scroll, and the only difference is that `blur` and `focus` events fire.
- **The server's changes win; the client's state survives otherwise.** For every reflected property of every component (`open`, `checked`, `pressed`, `collapsed`, `active`, `value`, `indeterminate`, ...), the element remembers what the server last rendered. An attribute the server changed since then, including one it removed, is applied; every other one keeps the client's value. So a dialog, drawer or accordion item the user opened, a toggle they pressed, a collapsed sidebar or the carousel's current slide survive a morph that does not change them, and the server can still close, uncheck or move them by rendering a different value. Groups that keep their state in their children (toggle-group, segmented-control, radio-group, checkbox-group, tabs) re-apply it to children the morph added or replaced. Text typed but not committed yet (number-input, editable) survives until it is committed, unless the server changes the value.
- **A selection the server removed falls back** instead of going blank: tabs whose selected panel is gone select the panel the server's `value` names, else the first enabled one; a select whose picked option is gone takes the server's `value`, else the first enabled option.
- **Attributes the component manages on itself** (`role`, `tabindex`, `aria-checked` and the like) are carried onto the incoming element whenever the server markup does not set them, so the morph leaves them alone. Anything the server markup sets is applied. If a page script keeps removing one of them, the component stops putting it back after ten attempts within a second (`@voidable/ui/dev` reports it).
- **Without the adapter** (a plain idiomorph or morphdom call, `innerHTML` on a parent, a framework replacing children) components still end up correct: one that loses its rendered DOM renders it again, attributes it manages are put back, and a cloned or re-parsed copy of a rendered element (a page-cache snapshot) renders exactly one set of its DOM. Focus and selection inside a rebuilt component are lost in that case.

`VoidDOM` covers every `<void-*>` element on the page, so you do not need `phx-update="ignore"` for components to survive patches. Use it only for a subtree you want LiveView to leave completely alone (it needs an id):

```heex
<div id="map" phx-update="ignore">…</div>
```

## Development warnings

A misspelled attribute, an invalid value or a child in the wrong parent does nothing and says nothing. Render `VoidableUI.Dev.warnings` once in the root layout, after your app script:

```heex
<script defer phx-track-static type="text/javascript" src={~p"/assets/app.js"}></script>
<VoidableUI.Dev.warnings />
```

It renders nothing outside the `:dev` environment, so a production page never loads it, and the browser console then reports each mistake with the element, the valid alternatives and a "did you mean", including markup LiveView patches in later. Configure it with `config :live_voidable, dev_warnings: false | true | :throw`. See [Development warnings](/getting-started/development-warnings/).

---
title: Composition and parts
description: How Voidable components take their content. Components with regions are written with explicit parts, plain void-* tags the component finds and wires up but never moves. The rules, every component's parts, and what is still to convert.
---

Voidable components render into the **light DOM**. Your children, classes, `id`s and framework bindings stay where you wrote them, in the same document as the rest of the page. Global CSS reaches into components, `querySelector` finds their parts, and a test library sees their roles and text.

A component that has **regions**, such as a title, a body, a trigger or a list of tabs, is written with **explicit parts**. A part is a plain `void-*` tag named after its component and region:

```html
<void-dialog>
  <void-dialog-title>Delete project</void-dialog-title>
  <void-dialog-description>This cannot be undone.</void-dialog-description>
  <void-dialog-actions>
    <void-button>Cancel</void-button>
    <void-button color="error" variant="filled">Delete</void-button>
  </void-dialog-actions>
</void-dialog>
```

The component finds its parts where they are and wires them up. It sets the roles, ids and ARIA links between them and handles focus and keyboard. It never moves, wraps or copies them. After the upgrade the DOM is the DOM you wrote, node for node, so a React, Vue, Svelte or Solid re-render, a Turbo or LiveView morph and an Alpine morph all find the nodes they expect.

## The rules

- **One way per component.** Each component has a single way of writing it. The implicit forms that came before (`heading="..."`, `slot="trigger"`, the tab-panel element, `text="..."` on a tooltip) are gone, and the [development warnings](/getting-started/development-warnings/) and `voidable check` report them with the correct markup.
- **Parts are regions, not styling.** Only a real region of the component becomes a part. Its name ends in one of `-trigger`, `-content`, `-title`, `-description`, `-body`, `-actions`, `-header`, `-footer`, `-item`, `-list` or `-separator`, following Radix and shadcn/ui where they have a name for it.
- **At most two levels.** A part can have parts of its own (`<void-tabs-list>` holds `<void-tabs-trigger>`, `<void-card-header>` holds `<void-card-title>`), and it stops there.
- **Plain tags, plain attributes.** You write no wrapper `<div>`s and no utility classes. A part that only needs styling is CSS-only: `@voidable/theme` styles it and no JavaScript defines it, so it costs nothing. Where a part does have behaviour, such as `<void-dropdown-menu-item>` or `<void-accordion-item>`, it is a registered element like any other.
- **A trigger wraps one control.** `<void-popover-trigger>`, `<void-dropdown-menu-trigger>`, `<void-hover-card-trigger>` and `<void-tooltip-trigger>` hold exactly one element, the `<void-button>`, `<button>` or link that gets the ARIA. The trigger part itself does not appear in the layout (`display: contents`).
- **Ids are yours.** The component generates an id only for a part that has none and never replaces one the author or the server wrote. When a part is removed, everything the component wrote on it is taken off again.

### Attribute or part?

**Attributes configure the component; parts hold its content.** If the author writes text or markup that appears on the screen as a region of the component (a title, a description, a body, the thing you press), it is a part, even when it is plain text. Settings that are not on the screen stay attributes: `size`, `variant`, `side`, `align`, `open`, `value`, `delay`, `hide-close`. `aria-label` stays an attribute. A component that generates all of its content from data (a calendar, a chart, pagination) has no parts.

## State lives on the parent

The component's state is the parent's reflected attributes: `open` on a dialog, popover or accordion item, `value` on tabs. Parts are styled from it with ordinary CSS, so the theme needs no class names:

```css
void-accordion-item[open] > void-accordion-content { display: block; }
void-tabs-content:not([active]) { display: none; }
```

Where a part has state of its own the component writes it as a plain attribute on the part: `active` on the selected `<void-tabs-trigger>` and the visible `<void-tabs-content>`. Server markup can write the same attributes, so the page looks right before the script loads.

## Opening and closing

The content of a collapsible and of an accordion item animates its height when `open` changes, with no script measuring it: the host is a two-row grid, and the content row goes from `0fr` to `1fr` (animating grid rows is widely available in every browser). The animation follows `--void-anim-scale` and is off under `prefers-reduced-motion`. Closed content is hidden from the accessibility tree, the tab order and find-in-page by the theme from the host's attribute (`visibility`), and the component also marks it `hidden="until-found"` once the closing animation is over, where the browser supports that (Chrome and Edge 102, Firefox 148; not yet Safari): the content stays hidden from assistive technology, and find-in-page, a text fragment or an in-page link to text inside it opens the panel first (`void-open` fires with `reason` `find`). Both components use the same mechanism, and a server morph keeps the open state, the attribute and a running animation.

## Before the script loads

`@voidable/theme/pre-upgrade.css` (included in the theme) gives every component its final layout before its JavaScript has run, so nothing shifts when it upgrades. The content of a closed popover, dropdown menu, hover card or tooltip is hidden until then, a closed dialog or drawer shows nothing, the first tab (or the one marked `active`) is visible, and a closed accordion item shows only its trigger.

## Dialogs and drawers

`<void-dialog>` and `<void-drawer>` are the one place the library uses a shadow root. A modal needs the browser's native `<dialog>` and `showModal()` (the top layer, an inert page behind it, Escape and the backdrop), and that element has to contain the content. Rather than move your nodes into a rendered `<dialog>`, the component keeps a small shadow root, `<dialog part="surface">`, a close button and a `<slot>`, and your parts stay unmoved children of the host. The dialog is named and described by your `-title` and `-description` parts through ARIA element references. The theme styles the surface with `void-dialog::part(surface)` and its backdrop with `void-dialog::part(surface)::backdrop`.

## Dismiss controls

An alert, a banner and a toast can be dismissed, and the control that does it is a region the author writes, like any other: a `-close` part that wraps the one button, the same shape as a trigger part.

```html
<void-banner color="info">
  <void-banner-description>Maintenance on Saturday.</void-banner-description>
  <void-banner-close><button type="button" aria-label="Dismiss">&times;</button></void-banner-close>
</void-banner>
```

Pressing the control fires `void-close` with `reason` `close-button` (it does not bubble; `preventDefault()` keeps the element on the page) and removes the element. Without a `-close` part there is no control, so the element cannot be dismissed (a toast still closes itself after its `duration`). The component renders no button of its own, and no shadow root, so the page, the framework and a server morph all see the control as ordinary markup. If focus was inside the element when it closed, it moves to the next focusable element after it (or the last one before it), so keyboard users are not sent back to the top of the page.

## Pickers

The three pickers were converted together, because they share the option element and the same question: who renders the control the user types in or presses.

```html
<void-field label="Plan">
  <void-select>
    <select name="plan" required>
      <option value="" disabled selected hidden>Choose a plan</option>
      <option value="free">Free</option>
      <option value="pro">Pro</option>
    </select>
  </void-select>
</void-field>

<void-field label="Country">
  <void-combobox name="country" placeholder="Search countries">
    <void-combobox-content>
      <void-option value="de">Germany</void-option>
      <void-option value="fr" selected>France</void-option>
    </void-combobox-content>
  </void-combobox>
</void-field>

<void-field label="Labels">
  <void-multiselect name="labels" placeholder="Pick labels">
    <void-multiselect-content>
      <void-option value="bug">Bug</void-option>
      <void-option value="docs" selected>Docs</void-option>
    </void-multiselect-content>
  </void-multiselect>
</void-field>
```

### Select: the native control, enhanced in place

`<void-select>` used to move the options into a `<select>` it rendered itself. Now you write the `<select>`: it carries `name`, `required`, `disabled`, `multiple` and `autocomplete`, and it is the form control, so submission, validation, reset, `<fieldset disabled>` and autofill are the browser's own and work before the script loads. A prompt is an ordinary first option, `<option value="" disabled selected hidden>`. The component names the select from its field, marks it invalid from `error`, styles it, and keeps `value`, `size`, `error` and the `void-change` event. A `value` attribute on the host is still the initial choice and the reset target, so the [state rule](/guides/server-rendered/) is unchanged. Where the browser supports the customizable select (`appearance: base-select`, Chromium today), the theme styles its picker as a float surface; elsewhere the native picker opens. There is no custom listbox. React, Vue, Svelte, Solid and Angular bind the native select directly (`value`/`onChange`, `v-model`, `bind:value`, `[(ngModel)]`).

### Combobox and multiselect: the content part

The option list is a part you write, `<void-combobox-content>` or `<void-multiselect-content>`, holding `<void-option>` elements. The component renders the input (combobox) or the trigger with its chips (multiselect) before it, as chrome. The content becomes the `role="listbox"` popup in the top layer, each option gets `role="option"` and an id, `aria-activedescendant` on the input points at the highlighted option (which also gets `active`), and `aria-selected="true"` marks the chosen ones. Filtering sets `hidden` on options that do not match and `empty` on the content when none does. No option is moved or copied.

### One option element

`<void-option>` takes `value`, `selected`, `disabled` and `label`. Its children are what the list shows, and may be rich (an avatar, a secondary line); `label` is the plain text shown in the input or chip once chosen, and defaults to the text content. Groups are not offered yet: a group would be a third level, and it waits for a need.

### What was considered

| | (a) content part, rendered input | (b) author-written native `<input>` | (c) keep the projection |
|---|---|---|---|
| Nodes never moved | Yes | Yes | No: options are moved into a rendered list |
| Typing through morphs (60 keys, a morph after each) | 0 lost under Turbo, morphdom and Alpine | 60 of 60 lost under Turbo and morphdom: the morph writes the server's `value` onto the input | 0 lost |
| Forms | Form-associated host | Native | Form-associated host |
| Layout shift on upgrade | None (pre-upgrade CSS hides the content) | None | None (options hidden until moved) |
| Guessable markup | Same shape as the dropdown menu | Needs an `<input>` with the right attributes | Options straight inside |
| Size of markup | One wrapper | One wrapper and an input | Smallest |

(a) was chosen. For the select, the same comparison favoured the native control: it is the most guessable markup there is, it works before the script, and a morph of the server's `<select>` is the native morph every server framework already handles. The measurements (Chromium, 5,000 options, medians of seven runs) were 30 to 60 ms for a first render of the select, against 115 to 195 ms for the projection; about 90 ms for the combobox and 85 ms for the multiselect, against 200 to 270 ms; and about 130 ms for a Turbo morph of either, against about 2 s. Two costs were found and avoided: writing `aria-selected="false"` on every option costs Chromium's accessibility tree about 5 s at 5,000 options, so only the chosen options carry the attribute; and a morph library resets a native select's selection when it syncs the options, so the component keeps the user's choice when the server did not change the selection, the `value` attribute or the options' `selected`.

## Frameworks and morphs

Parts are ordinary children, so every framework renders them directly. React has wrappers for them next to the components (`DialogTitle`, `TabsTrigger`, `PopoverContent` and the rest, generated from the manifest). Vue, Svelte, Solid, Angular, ERB, HEEx and Blade write the tags as they are. A part can arrive late, be reordered, re-keyed or removed, including while the overlay is open or the user is typing in it: the component looks its parts up when something changes and rewires them.

Before a morph (Turbo, LiveView, Livewire), the component copies what it wrote on its parts (generated ids, roles, `aria-*`, `active`) onto the server's version of the same parts, matched by id or by position, so the morph keeps them instead of stripping them. The usual [state rule](/guides/server-rendered/) still applies: a reflected attribute the server changes wins, client state it did not touch is kept.

## What to avoid

- **Do not put content directly in a component that takes parts.** A bare `<void-button>` inside `<void-popover>`, or a paragraph inside `<void-dialog>`, is reported with the correct markup and is not wired.
- **Do not set the attributes the component writes on its parts** (`role`, `aria-*`, `tabindex`, `active`, generated ids) unless a component page says so. The component puts back the ones it owns if something else changes them; an id you set is always kept.
- **Do not replace a component's `innerHTML` to update it** in a component that still projects (the **To convert** rows above). Components with parts take any child changes.
- **Do not wrap a component in another to restyle it.** Use the [theme tokens](/getting-started/tokens/), and see [patterns](/patterns/overview/) for page structure such as a shell, a page head or a toolbar.

## Parents

Some elements only work in the right container: a part only inside its component, `<void-dropdown-menu-item>` in a `<void-dropdown-menu-content>`, `<void-accordion-item>` in a `<void-accordion>`, `<void-option>` in a `<void-combobox-content>` or `<void-multiselect-content>`, and a `<void-select>` takes a native `<select>` holding native `<option>` elements. Each component page lists these under **Children and placement**, from the same data that `voidable check` and the [development warnings](/getting-started/development-warnings/) use, so a wrong parent is reported in the editor, in CI and in the console.

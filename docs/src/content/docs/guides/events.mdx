Components tell your app what happened by dispatching `CustomEvent`s whose names start with `void-`. They all follow the same rules:

- **They bubble and are composed**, so you can listen on the element or on any ancestor, which makes one listener on a `<form>` or a container enough for many controls. The exception is the open-state events, `void-open` and `void-close` (and the sidebar's `void-collapse` and `void-expand`): like the native `toggle` and `close` events they fire on the element that opens, closes or is dismissed and do not bubble, so a popover closing inside a dialog never looks like the dialog closing. That holds for every component that has them: overlays, the hamburger, nav menu items, toasts and banners. Listen on the element, or on an ancestor in the capture phase. They carry `detail.reason` (one vocabulary, listed in [API conventions](/guides/conventions/#events)), and `void-close` is cancelable when the user caused it. See [Overlays](/components/overlays/#events).
- **What changed is in `event.detail`**, an object whose fields are listed per event below and on each [component page](/components/overview/). `void-change` and `void-input` always carry `detail.value`, the component's new value in the type of its `value` property (an array for a multi-value control); a control whose state is a boolean also carries it by its attribute's name (`detail.checked`, `detail.pressed`).
- **`void-input` is per edit, `void-change` is a commit.** On every text-entry control (input, textarea, action input, compose input, number input, PIN input, editable), `void-input` fires on every keystroke and `void-change` when the value is committed, as the native `input` and `change` do. On controls with no in-between state, such as a switch, checkbox or select, `void-change` is the one event.
- **The native events still fire.** Controls that render a native input also let the browser's own `input` and `change` events bubble, so existing handlers work. Prefer `void-*`, whose `detail` is the same on every control.
- **Setting a property from script does not dispatch.** `el.value = 'x'` is not a user action, so no `void-change` follows. Only the user's interaction (and the control's own methods that stand in for it) fires events.

A misspelt event name never fires, and nothing complains; the [development warnings](/getting-started/development-warnings/) report a listener for a `void-*` name that no component dispatches.

## Listening

<div class="vd-api-table">

| Where | How |
| --- | --- |
| Plain JavaScript | `el.addEventListener('void-change', (e) => console.log(e.detail.value))` |
| Lit | `@void-change=${(e) => …}` in the template |
| Svelte 5 | `onvoid-change={(e) => …}` |
| React | `<Input onVoidChange={(e) => …} />` from `@voidable/ui-react` |
| Alpine / Livewire | `x-void-on:void-change="handler($event.detail)"` |
| Rails (Stimulus) | `data-action="void-change->search#filter"` |
| Phoenix LiveView | `phx-click` / `phx-change` / `phx-submit` first; for other events, `events` on a `live_voidable` component (the `VoidEvent` hook) forwards them with `pushEvent` |

</div>

The [framework pages](/frameworks/react/) have the details, including typing and the helpers that write these attributes for you.

Event delegation works as it does for any bubbling event (not for `void-open`, `void-close`, `void-collapse` and `void-expand`, see above):

```js
document.querySelector('form').addEventListener('void-change', (e) => {
  console.log(e.target.localName, e.detail);
});
```

## Reading state in a test

Because the events bubble and carry their data, a test can wait for one instead of sleeping:

```js
const changed = new Promise((resolve) => el.addEventListener('void-change', resolve, { once: true }));
el.click();
console.log((await changed).detail);
```

See [Testing](/guides/testing/) for finding components by role and name.

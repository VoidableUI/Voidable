This page records what two real screen readers said when a script moved through each component's test page. Every string in the tables below is copied from the spoken-phrase transcripts that the [Screen readers workflow](https://github.com/VoidableUI/Voidable/blob/master/.github/workflows/screen-readers.yml) uploads; none is written from memory or from the markup. Read it with the [accessibility statement](/guides/accessibility-statement/), which says what the project aims for and what it checks, and with the [accessibility guide](/guides/accessibility/).

**This is an automated run, not a test by people.** A script presses the screen reader's navigation keys and reads a log. It finds regressions and gross errors. It does not tell whether a flow is understandable, whether the wording is what a daily user expects, or how a component behaves with the settings, speech rate, braille display or habits of a real user. No person who relies on a screen reader has tested Voidable. Treat these results as evidence that the markup is exposed to the two readers below, not as a statement that the components are accessible to people who use screen readers.

Of the defects first listed in issue 75, none was confirmed as a component defect; the two changes to the multiselect were hiding its placeholder and chips from assistive technology and describing the trigger with the names of the chosen options (then the count beyond three).

## Known defects and unexplained results

The work is tracked in [issue 75](https://github.com/VoidableUI/Voidable/issues/75). Of the defects first listed there, none was confirmed as a component defect. Every item below is labelled passed, intermittent, reader behaviour (expected failure) or not confirmed. The data is run 45948762827 for both readers.

- **Multiselect on VoiceOver: not confirmed (expected failure).** After Enter chooses an option, VoiceOver says only `You are currently on a selectable (null), inside of a list box.`; NVDA says `selected`. The multiselect changed twice: the placeholder and chips are now `aria-hidden`, so VoiceOver's cursor does not rest on a child of the combobox, and the names of the chosen options are in the combobox description (up to three, such as `CSS and JavaScript`, then the first three and the count, `A, B, C, 5 selected`). Neither changed what VoiceOver says. Plain-HTML references with the same trigger children were silent on the first Enter too and spoke on the next one, so VoiceOver reports a choice late or not at all in plain HTML as well.
- **Dialog description on VoiceOver: reader behaviour (expected failure).** The name is spoken and the description is not, while NVDA speaks both. The description is correct in the accessibility tree, and a copy of it as `aria-description` made no difference.
- **Dropdown menu and number input on VoiceOver: intermittent.** Both passed on a retry. Focus moves to the first menu item and VoiceOver says `Rename menu item (1 of 3)` in most attempts and only `Actions menu pop up button` in others; a plain ARIA menu button was spoken the same way.- **Dialog on NVDA: intermittent.** The first attempt heard only `button` after activating the trigger; the retry heard `Profile settings, dialog, Change how your name appears.`
- **Radio group, accordion, tabs, table and chart data table on NVDA: passed.** They failed in earlier runs because of the script, not the components: the set-up had changed the first control or left the browser toolbar or focus mode in charge (so NVDA's keys said nothing); the scenarios now put NVDA in browse mode before the first move and in focus mode before arrow keys that must reach a radio. NVDA does not say a position for native or plain ARIA radios and tabs, so for NVDA the position is checked in the accessibility tree.

Fixed in earlier runs and confirmed: the number input value (VoiceOver spoke a percentage of the range, now `2 Seats stepper`) and the toast announcement.

## Intermittent results

A hosted runner is not a stable test bench, and a screen reader on it less so. In run 45948762827 `number-input` and `dropdown-menu` on VoiceOver and `dialog` on NVDA passed only after a retry. A scenario that passes only after a retry is counted as intermittent here, not as passing.

## What has not been tested

None of the following has been tested, by script or by a person:

- **Mobile screen readers:** VoiceOver on iOS and iPadOS, and TalkBack on Android. Touch exploration, swipe navigation and the rotor behave differently from the desktop commands the script uses.
- **JAWS**, and Narrator on Windows.
- **Orca** on Linux (Guidepup supports it; the project does not run it).
- **Other browser pairings:** VoiceOver with Chrome or Firefox, NVDA with Firefox or Edge, JAWS with anything.
- **Voice control** (Voice Control on macOS and iOS, Windows Voice Access, Dragon): whether every control can be addressed by its visible name.
- **Switch access** and keyboard-only scanning.
- **Screen magnification** and zoom to 400%, and text spacing overrides.
- **Braille displays.**
- **Languages other than English**, including a screen reader running in French or Arabic.
- **Real use:** tasks done by people who use these tools every day, which is the test that matters.

## Help with a mobile pass

If you use VoiceOver on iOS or TalkBack on Android, a short pass over the components below, reported with the [assistive technology report form](https://github.com/VoidableUI/Voidable/issues/new?template=assistive-technology-report.yml), is the most useful thing you can give this project. You do not need to read code. The component pages on this site show each component working.

1. Note your device, operating system version, screen reader and its version, and browser with its version. Turn off any setting you would not normally use.
2. Open a documentation page that has the component. Swipe to it with your usual gesture.
3. For each of these, say what was announced and whether you could finish the task: a button and an icon-only button; a text field with a required and an invalid state and its error; a checkbox, a radio group and a switch; a slider; a select and a combobox; a dialog (open it, read it, close it, see where focus lands); a dropdown menu; tabs; an accordion; a toast; a table; the date picker.
4. For each, record: the name you heard, the role you heard, the state you heard (checked, expanded, selected, invalid), and anything that was missing, wrong, repeated or confusing. Say plainly "it worked" when it did.
5. Report what you found, including that it all worked. A report of nothing wrong is as useful as a defect.

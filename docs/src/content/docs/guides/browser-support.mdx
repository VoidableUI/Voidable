Voidable targets current browsers and nothing older than the platform features it uses. It has no build step that compiles CSS down for older engines, no polyfills, and no support for Internet Explorer or the legacy Edge. This page lists what the code needs, what CI runs, and how the library behaves where a feature is missing.

**What is settled and what is not.** The table and the degradation notes below are derived from the source of `@voidable/theme` and `@voidable/ui`, and from the release versions of each platform feature. The minimum versions are the ones the code implies; the project has **not** tested any browser older than the current one in CI, so a minimum here means "the feature exists from this version", not "this was checked". A version marked "to confirm" has not been checked against a browser compatibility source. The support policy at the end is a proposal for the owner to confirm in the [road to 1.0](/guides/road-to-1-0/#platform), not a promise.

## The short version

Full fidelity needs, at least:

| Engine | Minimum implied by the code | What sets it |
|---|---|---|
| Chromium (Chrome, Edge, and other Chromium browsers) | 120 | `:dir()`; everything else is 114 or older, with the Popover API at 114 |
| Firefox | 128 | `@property` (Firefox 128); `:has()` is 121 |
| Safari (macOS and iOS) | 17 | The Popover API (17); `:has()` and `@property` are 15.4 and 16.4 |

Below these, the library still loads, because the components use feature detection for the scripting features, but some rules in the theme do not apply, as described under [what degrades](#what-degrades-in-an-older-browser). The theme's source comment says "Chrome 111, Firefox 113, Safari 16.2" for `color-mix()` and `oklch()`; that is the floor for colours alone, and the other rows in the table raise it.

Anchor positioning, `@starting-style` and the other newer features are not required: each has a fallback. Browsers that ship them (Chromium 125 and later, Firefox 147 and later, Safari 26 and later for anchor positioning) get the native behaviour.

The theme also uses relative features not listed because they are older than every row above (`:is()`, `:where()`, `:focus-visible`, custom properties, `calc()`, and `light-dark()` is **not** used). Nested CSS is not used, and the theme build (`lightningcss`) is given no browser targets, so it does not rewrite or lower anything: what is in the source is what ships.

## What is tested in CI

- **Browser suite** (`ci.yml`, job `browser`): every spec in Chromium, Firefox and WebKit, on Linux (`ubuntu-24.04`), each at the build that Playwright 1.65.1 bundles. The versions of those builds are **to confirm**. The WebKit build is Playwright's, which is the Safari engine but is not the Safari application or iOS Safari, and on Linux it is not WebKit as it ships on a Mac.
- **Chromium only:** axe-core, forced-colours emulation, the performance budgets, the visual review, and the server-backed suites (Rails, Phoenix, Laravel).
- **Not tested:** any browser version older than the one Playwright bundles; Microsoft Edge itself (it shares Chromium); Safari on macOS or iOS as installed; Chrome on Android; Firefox on Android; browsers with other engines; assistive technology other than the [scripted VoiceOver and NVDA runs](/guides/screen-reader-results/).
- **Screen readers:** the separate `Screen readers` workflow runs WebKit on macOS 15 and Chromium on Windows Server 2025. It does not gate a release.

## What degrades in an older browser

The aim is that a missing feature costs polish, not function:

- **Overlays.** Without anchor positioning, a built-in positioner places and flips the panel. Without the Popover API, the panel opens and closes through the `hidden` attribute and fixed positioning, but is not in the top layer, so a stacking context can hide it. Without `@starting-style` or `allow-discrete`, an overlay appears or disappears without a transition. Escape, outside presses and focus handling are scripted, so they do not depend on the browser.
- **Selects.** Without `appearance: base-select` the list is the browser's own. It works the same way and looks like the system.
- **Tabs and app shell.** Without scroll-driven animations the edge fade is missing.
- **Surfaces.** Without `backdrop-filter`, glass surfaces are solid.
- **Forms.** Without `attachInternals`, controls that submit through `ElementInternals` still work as controls and reset on the form's `reset` event, but submit nothing with a native form: the [forms guide](/guides/forms/) says how to read the value.
- **Right-to-left.** Without `:dir()`, a few mirrored details are left-to-right.
- **Before the script loads.** The theme styles the not-yet-defined state, so a server-rendered page measures the same before upgrade. See [Loading components](/getting-started/loading/#before-a-component-loads).
- **Not supported:** a browser without cascade layers, `color-mix()`, `oklch()`, `@property` or `:has()` loses the theme's core rules. The library is not designed to work there.

Where a feature does not degrade the way this list says, that is a bug: [open an issue](https://github.com/VoidableUI/Voidable/issues/new/choose).

## Support policy

The table implies a floor, not a policy. What the code supports is the engines and versions above. What the project **tests** is the current Playwright build of Chromium, Firefox and WebKit. Nothing in the repository says how long a version is supported, how a floor is raised, or whether Voidable promises anything for a browser below the latest.

This is a proposal, for the owner to decide in the [road to 1.0](/guides/road-to-1-0/#platform):

- State the floor of the table above as the supported minimum (Chromium 120, Firefox 128, Safari 17), as "best effort, not tested".
- Promise and test the **current stable release of each of Chrome, Edge, Firefox and Safari**, and the previous major of each, which is the usual evergreen policy. That is far above the floor, which makes the floor a statement of what the code allows rather than a promise.
- Raise the floor only in a minor release before 1.0 and in a major release after, with a line in the upgrade guide, as for any other breaking change.
- Treat engines Playwright cannot drive (iOS Safari and Chrome on Android as installed) as supported through their engines, until a test on a real device says otherwise.

None of these is decided. Open questions: whether the floor should be the table's or "the last two majors"; whether a real Safari on macOS and iOS should be added to CI; whether Firefox on Android and Samsung Internet are supported by name.

---
title: Design Philosophy
---

Every decision in Voidable traces back to a single requirement: a UI library that works inside a federated micro-frontend architecture.

## Built for Federation

A shell application connects to microservices via [Module Federation](https://webpack.js.org/concepts/module-federation/). Each microservice ships its own UI as a federated JavaScript module. Services carry only structure — no custom styling.

The shell owns the design system and pushes it down into components. This means theming must be entirely independent of the consuming service. A service cannot and should not influence its own appearance.

That constraint drove every major decision in Voidable.

## Light DOM

Components override `createRenderRoot()` to render into the Light DOM:

```js
createRenderRoot() { return this; }
```

No Shadow DOM, except for the dialog and the drawer, which keep a small one for the native `<dialog>` they are built on. The consequences of this are significant:

- Your CSS has full access to component internals
- Theme tokens flow naturally through the cascade
- No `::part()` or `::slotted()` workarounds (the dialog and drawer surface is the one `::part()` the theme uses)
- Services receive styling from the shell, not from themselves

Shadow DOM solves encapsulation. Voidable solves the opposite problem: components that are deliberately transparent to their environment.

## Devoid of Style

Voidable components contain zero intrinsic styling. No fixed heights, no hardcoded spacing, no embedded CSS. They are semantic containers that receive all visual properties from `@voidable/theme` via CSS custom properties.

The name reflects this: components are *void* of style. The theme package is the single source of visual identity. Swap the theme and every component changes. A service can't break the design system because it never owned the styling to begin with.

## Semantic Elements for AI

Custom elements like `void-button`, `void-input`, and `void-dialog` are semantic targets. AI agents using Playwright, Puppeteer, or other browser automation tools can target them directly:

```js
page.locator('void-button[variant="filled"]')
page.locator('void-input[name="email"]')
```

No ambiguous `div` class hierarchies. No shadow boundaries to pierce, except around the dialog and drawer surface. This was a core design consideration, not a side effect.

## CSS Token Architecture

Styling flows through four layers:

1. **Primitives** — fixed values: color palettes, weights, easings
2. **Knobs** — about a dozen inputs a theme sets: accent, neutral tint, contrast, chrome, radius, density, rhythm, type
3. **Tokens** — semantic values derived from the knobs: `--void-color-bg`, `--void-color-text`, `--void-color-border`
4. **Component CSS** — selectors that reference tokens only

All of it lives in `@voidable/theme`. Components import nothing. Dark/light mode switches via `data-theme` attribute — tokens remap, components follow automatically.

## Negative Space

"Void" as in the space between things. The default theme reads as light and airy, and it gets there with three decisions rather than with padding:

1. **Control size: modest.** Controls are 36px tall and share one height per size step. Padding inside a component makes each element heavier and pushes elements toward each other, so there is only as much as the control needs.
2. **Layout rhythm: generous.** The space between groups and sections is several times the space inside them (8 and 16px inside a group, 40px between groups, 72px between sections). This is where the airiness comes from, and it belongs to the page layout, not to components.
3. **Chrome: minimal.** Hairlines instead of boxes, containers with a fill you can barely see, content sitting directly on the page, and shadows only for things that overlap it.

Type does the rest: regular weights, small quiet uppercase labels, large plain numerals, and secondary text that is the same color at a lower opacity.

Each of the three is a knob (`--void-density`, `--void-rhythm`, `--void-chrome`), so a theme can be dense, or boxed, without touching a component. See [Theming](/getting-started/theming/).

## Framework Adapters

A framework gets its own package only when it needs runtime behaviour that `@voidable/ui` cannot provide (`@voidable/ui-react` for React wrappers and event bridging, `@voidable/ui-hotwire`, `@voidable/ui-alpine` and `@voidable/ui-liveview` for server-rendered stacks). Everything else is configuration plus typings generated from the component manifest and shipped in `@voidable/ui` (`@voidable/ui/types/*`, and `@voidable/ui/angular` for Angular forms). No adapter adds styling.

Server-side frameworks (LiveView, Hotwire) use a dual-package architecture: an npm package for client-side hooks and controllers, plus a native server-side package (Hex for Elixir, gem for Ruby) providing template helpers.

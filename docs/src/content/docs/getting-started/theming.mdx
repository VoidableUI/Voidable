Voidable separates structure from style. Components ship with **zero visual CSS**: all appearance comes from `--void-*` CSS custom properties defined in `@voidable/theme`.

The theme is built to be rethemed by changing a handful of inputs, by a person or by an AI agent. You do not edit hundreds of tokens. You set **knobs**, and every colour, size, radius and duration is derived from them in plain CSS, in both colour schemes, with no build step.

## The knobs

Set these on `:root`. Everything else follows.

```css
:root {
  --void-accent-hue: 250;       /* blue */
  --void-accent-chroma: 0.16;   /* 0 = no accent colour (the default) */
  --void-radius: 8px;
}
```

| Knob | Default | What it changes |
|---|---|---|
| `--void-accent-hue` | `250` | Hue of the accent, as an OKLCH angle in degrees: 30 red, 60 orange, 90 yellow, 150 green, 200 teal, 250 blue, 300 purple, 350 pink. Has no effect while chroma is 0. |
| `--void-accent-chroma` | `0` | How colourful the accent is. `0` means no accent colour: primary buttons, selection and switches are the inverse of the page (white on black, black on white). `0.10` to `0.20` gives a coloured accent. Lightness is chosen for you in each scheme so the accent keeps 4.5:1 as text and under text. |
| `--void-neutral-hue` | `60` | Hue of the greys: text, borders and surfaces. |
| `--void-neutral-chroma` | `0.004` | Tint of the greys. `0` is pure grey, `0.004` is barely warm, `0.02` is clearly tinted. Capped at `0.04`. |
| `--void-page-tint` | `0` | How much of the neutral tint the page background takes, 0 to 1. `0` is a pure black or pure white page. `1` is off-white paper in light and a lifted near-black in dark. |
| `--void-contrast` | `0.2` | Strength of secondary text and control borders, 0 to 1. `0` is the softest setting that still meets WCAG AA; `1` is the strongest. Values outside the range are clamped, so no setting takes text below 4.5:1. `prefers-contrast: more` raises it to 1. |
| `--void-chrome` | `0.3` | How much the containers draw, 0 to 1: the strength of divider lines and the fill of cards and panels. `0` is faint hairlines and no fills, `1` is clear lines and visibly filled containers. |
| `--void-radius` | `4px` | Corner radius of a control. Smaller and larger radii scale from it. `0px` is square; `999px` makes controls pills (cards and dialogs stop at 24 to 32px). |
| `--void-density` | `1` | Size of things inside components: control height (36px at 1), padding and the spacing scale. `0.8` is compact, `1.15` is roomy. |
| `--void-rhythm` | `1` | Space between groups and sections of a page, independent of density. |
| `--void-font-size` | `0.875rem` | Body text size. Every other text size scales from it. |
| `--void-font-sans`, `--void-font-mono` | Inter, JetBrains Mono | Typefaces. The theme names them but ships no font files: load them yourself (for example `@fontsource-variable/inter`), or the next family in each stack is used. |
| `--void-anim-scale` | `1` | Multiplies every duration. `0` switches animation off. `prefers-reduced-motion` sets it to 0. |

The knobs are declared, with the same explanations, in `@voidable/theme/knobs` (`src/knobs.css`).

### Try them: the theme builder

The [theme builder](/theme/) puts every knob on this page next to a real application (an overview, a data table, a form, a settings page and a page over a photograph), at desktop and phone width, in dark and light at once. It measures contrast as you go and gives you the theme four ways: the CSS to paste, a file to download, a link, and a description for an AI agent.

A link to the builder **is** a theme. Every knob is a URL parameter named after it without the `--void-` prefix, so a person or an agent can write one by hand:

```
https://voidable.dev/theme/?accent-hue=162&accent-chroma=0.19&radius=8&rhythm=1.1
https://voidable.dev/theme/?theme=dune&radius=0
https://voidable.dev/theme/?skin=loft&accent-hue=258&accent-chroma=0.15
```

| Parameter | Value |
|---|---|
| a knob, without `--void-` (`accent-hue`, `radius`, `font-size`, ...) | The knob's value. A bare number takes the knob's unit: `radius=8` is `8px`, `font-size=0.875` is `0.875rem`. `font-sans` and `font-mono` take a font-family list, or a short key: `inter`, `system`, `humanist`, `geometric`, `rounded`, `serif`, `mono` (and `jetbrains`, `system` for the monospace). |
| `theme` | A shipped theme to start from; the other parameters override it. |
| `skin` | `loft` (see [Skins](#skins-beyond-the-knobs)). |
| `name` | The theme's name, used for the selector and the file name. |
| `screen`, `scheme`, `device` | What the preview shows: `overview`, `table`, `form`, `settings` or `live`; `dark`, `light` or `both`; `desktop` or `phone`. |

Knobs you leave out keep their defaults, so the bare URL is the default theme. Values that are not valid for a knob are ignored. The same data (names, ranges, defaults, every shipped theme) is published as `@voidable/theme/knobs.json`.

## Writing a theme

A theme is a file that sets knobs and nothing else. The package ships eight; each is about a dozen lines.

```css
/* themes/dune.css — warm, rounded, comfortable */
[data-void-theme="dune"] {
  --void-accent-hue: 40;
  --void-accent-chroma: 0.15;
  --void-neutral-hue: 70;
  --void-neutral-chroma: 0.025;
  --void-page-tint: 1;
  --void-contrast: 0.3;
  --void-chrome: 0.9;
  --void-radius: 10px;
  --void-density: 1.12;
  --void-rhythm: 1.1;
  --void-font-size: 0.9375rem;
}
```

```css
@import '@voidable/theme';
@import '@voidable/theme/themes/dune.css';
```

```html
<html data-void-theme="dune">
```

| Theme | Character |
|---|---|
| `void` | The default, written out: monochrome, hairlines, 4px corners, 36px controls. |
| `dune` | Warm, rounded, comfortable: a terracotta accent, sand-tinted greys on a soft page, filled containers. |
| `console` | Dense and sharp: square corners, compact controls, a signal-green accent, monospace throughout. |
| `orbit` | Mission control, at rest: no accent colour, cool greys, lines you can barely see, almost square corners and a great deal of room. |
| `capsule` | Everything is a pill: fully rounded controls, no accent colour, faint chrome. |
| `aurora` | One electric colour: a vivid green accent on a pure page, cool greys, 8px corners. |
| `iris` | Violet, tinted through: a violet accent and greys of the same hue on a softly tinted page. |
| `paper` | Editorial: a serif the operating system already has, off-white paper, an ink-blue accent, larger text and wide margins. |

Each is one click away in the builder: [void](/theme/?theme=void), [dune](/theme/?theme=dune), [console](/theme/?theme=console), [orbit](/theme/?theme=orbit), [capsule](/theme/?theme=capsule), [aurora](/theme/?theme=aurora), [iris](/theme/?theme=iris), [paper](/theme/?theme=paper).

Every theme works in dark and in light. You do not write a second block for light: both schemes are the same formulas.

### Contrast is checked for you

`mise run lint:contrast` evaluates the derived colours for the default knobs, for every file in `themes/` and `skins/`, and for the extremes of each colour knob, in both schemes. It fails if any text pair drops below 4.5:1 or any control border below 3:1, and if a theme file sets anything other than a knob. The theme builder shows the same measurement live for the theme you are making.

## Skins: beyond the knobs

A theme changes values. A **skin** changes structure: what a container is, whether anything has a line around it, what casts a shadow. It is a separate stylesheet that overrides derived tokens and, where a component offers no token, restyles the element itself. It never edits a component's own CSS, and it composes with every knob and every theme.

The package ships one, **Loft**: a soft tinted page, containers that are lighter than the page and float on a shadow, and no hairlines around anything.

```css
@import '@voidable/theme';
@import '@voidable/theme/skins/loft.css';
```

```html
<html data-void-skin="loft">
```

Put the attribute on `<html>`, or on an element that also carries `data-void-theme`. Live, the default look and Loft, each with the default knobs and with Dune:

### What a skin could not reach

Loft was written to find out how far a theme author gets without touching component CSS. Its file has two parts: one rule of token overrides, then the rules that had to name an element because no token existed. The first part did less than half the work. The second part is the list of override points the components and patterns are missing:

| # | Element | What Loft needed | Why a token could not do it |
|---|---|---|---|
| 1 | `void-nav-bar` | A lifted surface and a shadow in place of the bottom rule | It reads the page colour and the shared divider colour directly; it has no background, border or shadow token |
| 2 | `void-page-head` | No rule under the title | The rule is the shared divider colour, so removing it by token removes every divider |
| 3 | `void-section` | A surface: background, padding, radius, shadow | The pattern has no surface at all, as tokens or as an attribute |
| 4 | `void-figures`, `void-figure` | Tiles with a gap in place of hairline-divided cells | The row draws its dividers and paddings itself, with selectors specific enough that an override has to match them |
| 5 | `void-rows`, `void-description-list`, `void-table` | Rules between items only, not above the first and below the last | No token or attribute separates the outer rules from the inner ones |
| 6 | `void-button` | A soft edge and a shadow on the outline button | The border colour is `--tone-border`, a private, unprefixed property declared on the button itself, so an ancestor cannot set it; there is no shadow token |
| 7 | `void-card`, `void-panel` | A shadow on the default container | Only the `elevated` variant casts one, and it also changes the fill |
| 8 | `void-alert` | The container radius and no border | It takes the control radius and a tone border with no token for either |

Three more things the tokens could not express, which Loft works around or leaves alone:

- **The derived tokens are declared on a closed list of elements** (`:root`, `[data-theme]`, `[data-void-theme]`, `[data-shape]`, the surfaces). A skin cannot add its own attribute to that list, which is why `data-void-skin` has to sit on one of those elements.
- **The media and glass surfaces derive their own tokens**, so a skin's token overrides stop at a `void-glass` panel and have to be repeated for it.
- **The colour scheme a theme prefers cannot be set by the theme.** Loft is designed light-first, but dark stays the default unless the page sets `data-theme`.

Where a component token did exist it worked: `--void-color-control-fill` gave every outline button and badge a filled surface, `--void-table-surface` repainted the table's sticky cells, and the radius, shadow and surface tokens restyled dialogs, menus, inputs and cards with no selectors at all. Component tokens for the eight rows above ([#46](https://github.com/VoidableUI/Voidable/issues/46)) would reduce Loft to its first rule.

## Tokens for design tools

The theme is CSS, computed in the browser. For tools that cannot run CSS, the package also ships every token **resolved**, for each theme and skin in both colour schemes:

| Import | What it is |
|---|---|
| `@voidable/theme/dtcg/<theme>.<scheme>.tokens.json` | [Design Tokens Community Group](https://www.designtokens.org/TR/2025.10/format/) format (Format Module 2025.10, the first stable version), for Tokens Studio, Style Dictionary and anything else that reads it. For example `dtcg/dune.light.tokens.json`. |
| `@voidable/theme/dtcg/voidable.resolver.json` | A DTCG resolver document (Resolver Module 2025.10) that lists those files as the contexts of one `theme` modifier. |
| `@voidable/theme/json/<theme>.<scheme>.json` | A flat map of custom property to resolved CSS value: `{ "--void-color-bg": "#000000", ... }`. |
| `@voidable/theme/knobs.json` | The knobs as data: name, range, step, unit, default and description, every shipped theme's values, and the builder's URL. |
| `@voidable/theme/names` | A TypeScript module: `tokenNames`, `knobNames`, `themeNames`, `skinNames`, the types `TokenName`, `KnobName`, `ThemeName`, `SkinName`, and `cssVar(name)`. |

```ts
import tokens from '@voidable/theme/json/dune.light.json' with { type: 'json' };
import { cssVar, type TokenName } from '@voidable/theme/names';

tokens['--void-color-bg'];            // the resolved page colour, as hex
const gap: TokenName = '--void-gap-group';
element.style.gap = cssVar(gap);      // "var(--void-gap-group)"
```

In the DTCG files `--void-<group>-<name>` is the token `<group>.<name>` (`color.bg`, `space.4`, `radius.md`), the knobs are `knob.<name>`, and the type roles are also given as composite `typography.<role>` tokens. Colours are sRGB components with a hex fallback; lengths keep `rem` where the source is in `rem`. Values the format has no type for (keywords, `em` tracking, and the three tokens that depend on the viewport) are listed under `$extensions` and are in the flat JSON as CSS text.

The values are computed at build time by a small evaluator in the package, so building needs no browser, and a test compares every exported value, for every theme, with what Chromium computes from the same CSS. For a theme of your own, the builder's **Design tokens** tab exports the knobs or the resolved tokens in the same format.

## Theming part of a page

Knobs can be set on any element that carries the `data-void-theme` attribute (with a theme name, or empty). Everything under it is restyled:

```html
<section data-void-theme style="--void-radius: 0px; --void-density: 0.85">
  …square, compact controls in here…
</section>

<aside data-void-theme="console">…a console-themed panel…</aside>
```

Live: the first box sets two knobs inline, the second names a theme, and the third nests a light region inside a themed one. The page around them is untouched.

The attribute matters. Custom properties that are computed from other custom properties are resolved where they are declared, so the theme re-declares its derived tokens on `:root` and on every element with `data-theme`, `data-void-theme` or `data-shape`. A knob set on an element without one of those attributes changes nothing below it.

## Dark and light

Dark is the **default**. Set `data-theme` on `<html>`, or on any element, to choose a scheme explicitly; without it, the page follows the operating system.

```html
<html data-theme="light">
```

```js
function toggleTheme() {
  const current = document.documentElement.getAttribute('data-theme') ?? 'dark';
  document.documentElement.setAttribute('data-theme', current === 'dark' ? 'light' : 'dark');
}
```

Each framework guide shows a few lines that track this attribute reactively (the React adapter ships a `useTheme` hook).

## Shape

`data-shape="sharp"` on any element zeroes every radius under it; `data-shape="curvy"` restores the theme's radius. It is a preset for the radius knob.

## Type roles

Text in an interface does a small number of jobs. Each job is a **role**: a group of tokens for family, size, line height, weight, tracking, case, colour and numeric features. Components use the roles, and one attribute applies a role to your own markup:

```html
<span data-void-type="label">Stations online</span>
<span data-void-type="value">41</span> <span data-void-type="unit">of 44</span>
<span data-void-type="caption">2 in maintenance, 1 degraded</span>
```

| Role | Job | Default |
|---|---|---|
| `label` | The small quiet name of a thing: table headers, stat labels, crumbs, section meta | Mono, 11px, medium, uppercase, 0.08em tracking, secondary colour |
| `value` | The number or word a stat is about | Sans, 30px, regular, tabular figures (`data-size="sm"` and `"lg"` for 20px and 36px) |
| `unit` | Set after a value: "TB", "ms", "of 44" | 14px, secondary colour |
| `caption` | The supporting line under a value, field or row | 12px, secondary colour |
| `heading` | A section heading | 18px, medium |
| `title` | The page title | 24px, medium |
| `display` | The headline of a hero or a media surface | 36 to 64px with the viewport, line height 1.05, tight tracking |
| `lede` | The sentence under a display headline | 16px, line height 1.5, secondary colour |
| `body` | Running text | 14px, line height 1.5 |
| `code` | Ids, configuration, anything typed exactly | Mono, 13px, tabular figures |

Restyle a role once and it changes everywhere, in components and in your markup:

```css
:root {
  --void-type-label-family: var(--void-font-sans);
  --void-type-label-case: none;
  --void-type-heading-weight: var(--void-weight-bold);
}
```

Role tokens are the second layer of theming, below the knobs: reach for them when a knob cannot express what you want.

## Design values

The default look is light and airy, and it gets there with three decisions. Each is a knob, so a theme can move it.

**Control size: modest** (`--void-density`). Controls are 36px tall and every control shares the height of its size step, so a mixed row lines up:

<div class="vd-example not-content">
  <div class="vd-row">
    <void-input placeholder="Search stations" style="width: 14rem"></void-input>
    <void-select aria-label="Region"><option>All regions</option></void-select>
    <void-segmented-control value="all" aria-label="State">
      <void-segmented-control-item value="all">All</void-segmented-control-item>
      <void-segmented-control-item value="online">Online</void-segmented-control-item>
    </void-segmented-control>
    <void-button>Schedule</void-button>
    <void-button variant="filled">Add station</void-button>
  </div>
</div>

**Layout rhythm: generous** (`--void-rhythm`). The space between groups is several times the space inside them. That is where the airiness comes from, and it belongs to the page layout, not to components.

**Chrome: minimal** (`--void-chrome`). Hairlines instead of boxes, containers with a fill you can barely see, tables and lists directly on the page, and shadows only for things that overlap it. The screen below has no box in it:

## Layout rhythm

The theme provides the distances as tokens, for your page layout:

| Token | Default | Use |
|---|---|---|
| `--void-gap-tight` | 8px | A label to its control, an icon to its text |
| `--void-gap-inside` | 16px | Items in a row or a group |
| `--void-gap-stack` | 24px | Blocks stacked in a group: fields in a form |
| `--void-gap-group` | 40px | Between groups |
| `--void-gap-section` | 72px | Between sections of a page |
| `--void-gutter` | 16 to 48px | Page side padding, by viewport width |
| `--void-measure` | 34rem | Line length for running text |
| `--void-measure-page` | 72rem | Width of a page column |

The first three follow `--void-density`; the group, section and gutter distances follow `--void-rhythm`.

## Overriding a single token

Any derived token can still be overridden directly. Put the override on the same elements the theme derives on, so it also holds inside nested scheme or theme regions:

```css
:root, [data-theme], [data-void-theme] {
  --void-color-success: #22c55e;
}
```

Prefer a knob where one exists: an override is one value, a knob moves everything that depends on it.

## Importing the theme

Full theme (recommended):

```css
@import '@voidable/theme';
```

That resolves to one built file, `dist/void.css` (`dist/void.min.css` is the minified copy). It carries the tokens, the scoped reset, the `html` and `body` base, the type roles, every component and pattern, the pre-upgrade rules and the forced-colours rules, each in its own [cascade layer](#cascade-layers).

Parts of it, when you want less:

```css
@import '@voidable/theme/tokens';     /* primitives, knobs and everything derived, in one file */
@import '@voidable/theme/reset';      /* the reset, scoped to void-* elements */
@import '@voidable/theme/base';       /* html and body (margin, font, colour, background) */
@import '@voidable/theme/type';       /* data-void-type roles */
@import '@voidable/theme/core';       /* everything except base: touches nothing outside void-* */
@import '@voidable/theme/themes/dune.css';
```

The full theme sets `html` and `body` (margin, font, colour, background) through `base`, in the `components.void.reset` layer. Everything else in it matches only `void-*` elements and what they contain. Use `core` instead of the full theme if the page's `html` and `body` are yours to style.

### Per-component CSS

Every component and pattern also has its own file, generated from the same sources, so a page that uses three components need not load sixty:

```css
@import '@voidable/theme/tokens';
@import '@voidable/theme/components/button.css';
@import '@voidable/theme/components/input.css';
@import '@voidable/theme/patterns/page.css';
```

Each file declares the layer order, carries the reset for its own tags, the rules for the not-yet-defined state and the forced-colours rules for that component, and pulls in the files of any component it renders (a combobox brings its listbox parts, for instance). Always load `tokens` first or alongside: the files use the tokens but do not repeat them. `dist/exports.json` lists every file and the tags it styles.

The JavaScript side does not load CSS for you. Pair the two yourself: the components you import, or let the autoloader register, are the components whose CSS you link. Until a component's script runs, the pre-upgrade rules in its file keep the page from jumping, so the pairing is a matter of bytes, not of correctness.

## Cascade layers

The theme puts everything in named layers, declared once and in this order, lowest first. They are children of `components`, the layer Tailwind v4 and most other setups use for component styles:

```css
@layer theme, base,
       components.void.reset, components.void.tokens, components.void.themes, components.void.type,
       components.void.components, components.void.patterns, components.void.skins, components.void.a11y,
       utilities;
```

- `components.void.reset`: the reset, scoped to `void-*` elements, and the `html` and `body` base.
- `components.void.tokens`: primitives, knobs and the derived tokens.
- `components.void.themes`: the theme files (they set knobs only).
- `components.void.type`: the `data-void-type` roles.
- `components.void.components` and `components.void.patterns`: every component and every CSS-only pattern.
- `components.void.skins`: a [skin](#skins-beyond-the-knobs). It overrides derived tokens and restyles elements of components and patterns directly, so it has to beat both whatever their selectors' specificity.
- `components.void.a11y`: forced-colours adjustments. Above the skins, so a skin can never hide a focus ring or a forced colour.

`theme` and `base` are the framework layers under the theme (Tailwind's preflight is in `base`) and `utilities` is above it, so utility classes such as `rounded-none` or `p-8` win over a component's styles without `!important`. Your own rules written directly in `components` win over the theme's sublayers too.

Why children of `components` and not top-level layers? A layer's position among the top-level layers is fixed by whichever `@layer` statement names it first. An app that loads Tailwind first (it declares `theme, base, components, utilities`) would otherwise get top-level `void.*` layers appended after `utilities`, and every Voidable component would beat every utility class. As children of `components` the order is the same whichever stylesheet loads first. Every stylesheet the theme ships repeats the statement.

### Overriding styles

Layered rules lose to unlayered ones, whatever their specificity, so your application stylesheet needs no `!important` and no selector tricks:

```css
/* app.css: not in a layer, so it wins over every layer of the theme */
void-button {
  border-radius: 999px;
}

void-card {
  --void-card-padding: var(--void-space-8);
}
```

Three things follow, and they are worth knowing:

- **Put your own reset in a layer.** An unlayered reset (`* { margin: 0; padding: 0 }`, Meyer, a classic normalize) also beats the theme and will flatten component spacing. Load it into a layer below the theme instead: `@import 'reset.css' layer(base);`. Tailwind v4 preflight is already in `base`.
- **`!important` is inverted between layers.** An important rule in an earlier layer beats an important rule in a later one, and any layered important beats an unlayered one. The theme uses `!important` in only two places (reduced motion and forced colours), both in the topmost layers; do not fight them with your own `!important`.
- **Order of your own layers.** To put your own code between Voidable and Tailwind utilities, write it in the `components` layer itself (`@layer components { .my-card { ... } }`), which beats the theme's sublayers, or leave it unlayered.

`[data-void-theme]` and `[data-theme]` regions cascade as before: the theme files set knobs, and the tokens derive from them on `:root`, `[data-theme]` and `[data-void-theme]`, so nested regions work in any layer arrangement.

## Browser support

The derivation uses `oklch()`, `color-mix()` and `calc()` inside both: Chrome 111, Firefox 113 and Safari 16.2, all released in 2023. It does not use relative colour syntax or `light-dark()`.

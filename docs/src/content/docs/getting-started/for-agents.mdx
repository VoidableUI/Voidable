Voidable is built to be written by agents as well as people, and everything on this site is generated from, or checked against, the same data an agent can query directly. This page is the short route.

## Read the docs as text

| What | Where |
| --- | --- |
| What the library is and where the complete text is | [`/llms.txt`](/llms.txt) |
| Every page in full, including the reference for every component | [`/llms-full.txt`](/llms-full.txt) |
| One component | `/components/<name>/`: for example [`/components/button/`](/components/button/) |
| The patterns for page structure | [`/patterns/overview/`](/patterns/overview/) |

Each component page has the same sections: a description, a live example with its HTML, JSX, ERB, HEEx and Blade source, an attribute table (type, values, default), events with their `detail`, where children go, how it behaves in a form, its keyboard keys, accessibility notes and the common mistakes. The tables are generated from the library's Custom Elements Manifest, so they match the code that ships.

## Use the `voidable` tool

The `voidable` command-line tool carries the same knowledge, offline, and checks what you write. It is one static binary: it needs no Go and no Node.

### Install it

On Linux or macOS, the installer downloads the binary for your OS and CPU from the latest [GitHub release](https://github.com/VoidableUI/Voidable/releases), refuses to continue unless its SHA-256 matches the release's `checksums.txt`, and puts it in `~/.local/bin` (no `sudo`):

```bash
curl -fsSL https://voidable.dev/install.sh | sh
```

Pass a release and a directory with `sh -s -- --version X.Y.Z --dir <path>`. `voidable version` prints what you have.

To do it by hand, download `voidable_<os>_<arch>.tar.gz` (`.zip` on Windows) for `linux`, `darwin` or `windows` on `amd64` or `arm64` from the release page, compare its SHA-256 with `checksums.txt`, unpack it and put `voidable` on your `PATH`. Each archive has a signed build-provenance attestation that records which commit and workflow built it:

```bash
gh attestation verify voidable_linux_amd64.tar.gz --repo VoidableUI/Voidable
```

The tool is not installable with `go install`: the library files it embeds are build output, not committed source.

### Commands

| Command | Does |
| --- | --- |
| `voidable ref` | One line per element. `voidable ref void-select` prints its attributes with types, allowed values and defaults, events, parents and an example. |
| `voidable check <file or dir>` | Finds unknown elements and attributes, invalid values, a boolean written as `"false"`, children in the wrong parent and controls with no accessible name (`missing-name`: an icon-only button without `aria-label`, an input with no label, a dialog with no heading). One problem per line as `file:line:col`; exit 1 when there are any. Reads HTML, ERB, HEEx, Blade, JSX, Astro, Vue, Svelte, Lit and Markdown. |
| `voidable gen snippet <tag> --lang html\|jsx\|erb\|heex\|blade` | Prints a working example of one element in the language you are writing. |
| `voidable mcp` | Serves the same three as MCP tools (`voidable_ref`, `voidable_check`, `voidable_snippet`) plus the skill, over stdio. |
| `voidable skill install` | Writes the Agent Skill into `.claude/skills/voidable`, for clients that load skills from disk. |
| `voidable install --dir <path>` | Writes the built library, `lit` and the theme into a project, for pages with no bundler. See [Loading components](/getting-started/loading/). |
| `voidable version` | Prints the version, commit and build date. Makes no network call; no command does. |

### Connect it to an agent over MCP

An MCP client starts `voidable mcp` itself, so it has to find the binary: either `voidable` is on the `PATH` the client runs with (the installer's `~/.local/bin` often is not, for editors started from a launcher), or the configuration gives the absolute path. For Claude Code:

```bash
claude mcp add voidable -- voidable mcp
claude mcp add voidable -- /home/you/.local/bin/voidable mcp   # when it is not on the client's PATH
```

Most other clients take the same thing as JSON:

```json
{ "mcpServers": { "voidable": { "command": "/home/you/.local/bin/voidable", "args": ["mcp"] } } }
```

Run `voidable skill install` in a project to write the skill to `.claude/skills/voidable` as well.

### Accessible names (`missing-name`)

`voidable check` reports a control that has no accessible name: a `<void-button>` with only an icon and no `aria-label`, a `<void-input>`, `<void-select>`, `<void-slider>`, `<void-textarea>` or other form control with no label (no enclosing `<void-field label>` or `<label>`, no `<label for>`, no `aria-label` or `aria-labelledby`), a `<void-dialog>` or `<void-drawer>` with no `heading` or `aria-label`, an avatar with no `alt`. A `placeholder` is not a name. Which components need one, and which attributes, text or ancestors supply it, is data in the Custom Elements Manifest (`accessibleName` in `packages/ui/cem/supplement.js`), not a list in the tool.

It reports only what it is sure of. A value it cannot evaluate counts as a possible name and is never reported: an expression (`aria-label={label}`, `:aria-label`, `<%= t("close") %>`, `{{ __('Close') }}`), a spread or attribute bag (`{...props}`, `{@rest}`, `{{ $attributes }}`, `v-bind="$attrs"`), a slot or yielded content, a framework component inside the element, or a framework component around a control that needs a field. The same rule runs in the browser as a [development warning](/getting-started/development-warnings/#accessible-names), where the name can be computed from the live page.

Run `voidable check` on every file you write, and fix what it reports before showing the result. Run `import '@voidable/ui/dev'` in development so the browser reports what static checking cannot (see [Development warnings](/getting-started/development-warnings/)).

## Rules that avoid the common mistakes

- **Use components for controls, patterns for layout.** Page structure (a shell, a page head, a section, a toolbar, a label and value) comes from [patterns](/patterns/overview/). Do not write layout CSS for them.
- **Look attributes up; do not guess.** `color="primary"` on a button, a `label` attribute on an input (use `<void-field label>`), and `<void-option>` inside `<void-select>` (which takes native `<option>`) all do nothing. Every component page has a **Common mistakes** section, and `voidable ref` is the same data.
- **A boolean attribute is on when present.** `disabled="false"` is still disabled. Remove the attribute. The few that default to on accept `="false"`; they are [listed here](/components/overview/#attributes-shared-across-components).
- **A control is a form control.** Give it a `name` and put it in a `<form>` (see [Forms](/guides/forms/)). Do not mirror its value into script state.
- **Listen to `void-*` events,** not to clicks on internals. See [Events](/guides/events/).
- **Do not style with raw values.** Colours, spacing and type come from the [tokens](/getting-started/tokens/).
- **Test by role and name.** [Testing](/guides/testing/) lists how to find each element.

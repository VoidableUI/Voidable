title: Testing in real browsers
description: How the real-browser suite and the server-backed framework suites are run, and how they report known defects.
---

Voidable is tested where it runs. Unit tests cover logic, but custom elements, focus, keyboard behaviour, accessibility trees and framework patching only exist in a real browser, so the repository has a Playwright suite in `tests/browser/` and a second one that drives real server frameworks.

## The browser suite

Every spec runs in Chromium, Firefox and WebKit against the built packages, then a Chromium-only set of performance and bundle-size budgets runs.

```bash
mise run test:browser:install                 # once: download the browsers
mise run test:browser                         # build, then every spec on every engine, then the budgets
VOID_BROWSERS=chromium mise run test:browser  # one engine
mise run test:browser -- specs/forms.spec.ts --project=firefox
```

Locally an engine that cannot start is skipped with a warning. In CI every engine must run. Where WebKit cannot run on your distribution, start Playwright's server in its Docker image and point `VOID_WEBKIT_WS` at it.

Overlays get their own stress spec. With real mouse and keyboard input it nests four overlays (drawer, dialog, popover, menu), opens them inside clipped, transformed and scrolled containers, opens each one at all four viewport corners at 1440x900 and 390x844, checks where focus goes when the opener has been removed, that a page can cancel a `void-close`, which `detail.reason` each way of closing reports, that fifty open and close cycles leave no nodes, listeners, top-layer entries or scroll lock behind, and that an open overlay survives a Turbo, morphdom or Alpine morph.

## The server-backed suites

`mise run test:server` starts real applications on the built packages and drives them in Chromium:

| App | Where | What it covers |
| --- | --- | --- |
| Rails | `packages/hotwire/demo` | Turbo 8 page-refresh and stream morphs, Turbo Drive with the page cache and back and forward, Turbo Frames, Turbo Streams |
| Phoenix LiveView | `packages/liveview/demo` | live navigation and patches, `phx-change` forms, server timers, server-opened overlays, the event bridge hooks |
| Laravel Livewire | `examples/laravel` | `wire:navigate`, `wire:poll`, `wire:click`, server-driven values and overlays, the Alpine event bridge |

Each app is described in `tests/browser/server/apps.mjs` and started by `tests/browser/server/start.mjs`, which bundles the built packages into the app, prepares it (dependencies, database) and runs it. `VOID_SERVER_APPS=phoenix mise run test:server` runs one. Each needs its toolchain from `mise.toml` (Ruby, Erlang and Elixir, or PHP), taken from mise when it is installed there and from `PATH` otherwise. Steps that fetch packages (bundler, hex, composer) are retried up to three times. The apps use ports 4520, 4530 and 4540; `VOID_RAILS_PORT`, `VOID_PHOENIX_PORT` and `VOID_LARAVEL_PORT` change them, so two checkouts can run side by side. The same specs check what a user would: typed text and focus that survive a server update, an open overlay that stays open, a value the server changes winning over the user's, and the same controls submitting the same values.

## Known defects

A test for a defect that is not fixed asserts the correct behaviour and starts with `expectedFailure('#61', 'what goes wrong')`. The key names a GitHub issue in `tests/browser/helpers/known-issues.ts` (or `untracked:` when no issue exists yet). The test still runs and is reported, but does not turn the suite red; when the defect is fixed, Playwright reports "expected to fail but passed" and the marker is removed with the fix. `VOID_RUN_EXPECTED=1` runs every marked test as an ordinary test.

## Visual review

The browser suite checks behaviour; `tests/browser/shots` checks how it looks. It photographs the reference pages (a dashboard, a queue table, a form with an open dialog, settings, empty states, a page over a photograph, a sheet of every component and the interaction states hover, focus, pressed, disabled and invalid, and every open overlay) at 1440x900 and 390x844, in dark and light, in every shipped theme and skin, and builds a gallery to review them side by side. The current gallery of the main branch is at [/gallery/](/gallery/).

```bash
mise run shots                       # capture everything, build tmp/shots/gallery/index.html
mise run shots -- --page sheet --theme void,paper --scheme dark --width 390
mise run shots:compare -- master     # before/after of the working tree against master
```

`shots:compare` builds each ref in a temporary worktree and shows the images that changed, worst first, as side by side, an overlay slider and a highlighted difference. The captures are byte-identical on one machine (fonts bundled, animations finished, fixed clock, software rendering) and differ between machines, so no screenshot is stored: on a pull request, CI photographs the base and the head on the same runner and uploads the before/after gallery. A difference is expected when the change touches the theme, a component or the reference pages and fails the job otherwise, unless a commit says `Visual-Change: <why>`. The job is skipped in the release path.

## In CI

The `browser`, `server` (Rails), `phoenix` and `laravel` jobs of `.github/workflows/ci.yml` run on every pull request. The release workflow calls the same file, so nothing is tagged or published unless every one of them passed. CI installs Ruby, Erlang/Elixir and PHP with `ruby/setup-ruby`, `erlef/setup-beam` and `shivammathur/setup-php`, which download prebuilt toolchains, at the versions pinned in `mise.toml`.
